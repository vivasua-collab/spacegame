## 1. Общие принципы

### 1.1 Размещение зданий

Здания размещаются на поверхности планеты по **гекс-сетке**. Каждый гекс может содержать одно здание. Размер гекс-сетки определяется радиусом планеты:

| Радиус планеты (g-класс) | Гексов на планете | Пример |
|--------------------------|-------------------|--------|
| Крошечная (R < 0.3) | 19 | Меркурий |
| Малая (0.3 ≤ R < 0.7) | 37 | Марс |
| Средняя (0.7 ≤ R < 1.3) | 61 | Земля |
| Большая (1.3 ≤ R < 2.0) | 91 | Суперземля |
| Огромная (R ≥ 2.0) | 127 | Мегаземля |

> **Примечание**: Размеры планет и количество гексов определены в [30-planets.md §2.1](./30-planets.md#21-радиус). Данная таблица приведена для справки.

> **Примечание для программиста**: гекс-сетка — стандартная axial-координатная система (q, r). Соседние гексы определяются шестью направлениями: [(+1,0), (-1,0), (0,+1), (0,-1), (+1,-1), (-1,+1)].

### 1.2 Уровни зданий

Каждое здание имеет **уровень от 1 до 10**. Повышение уровня:
- Увеличивает скорость работы (добыча, переработка, производство)
- Снижает стоимость эксплуатации (энергия на 1 единицу продукции)
- Может открывать доступ к новым рецептам / ресурсам
- Требует ресурсов для улучшения и времени строительства

### 1.3 Автоповтор задания

Как в оригинале «Полдень XXI века»: здание **запоминает последнее задание** и автоматически повторяет его, пока:
- Есть необходимые входные ресурсы на складе
- Есть энергия
- Игрок не отменил задание явно

### 1.4 Энергопотребление

Каждое здание потребляет энергию. Если энергии недостаточно:
1. Здания с **низшим приоритетом** отключаются первыми
2. Приоритет задаётся игроком (по умолчанию: добыча → переработка → производство → исследование)
3. Отключённое здание не производит, но и не потребляет ресурсы

### 1.5 Шкала измерения (важно!)

### 1.6 Раздельная система складов

> Подробности — в [35-warehouse-and-logistics.md](./35-warehouse-and-logistics.md) §1.3.

Ресурсы хранятся в **3 типах складов**:

| Тип | Вместимость | Что хранит |
|------|-------------|------------|
| Рудный (открытый) | 1.0 + 0.25 × Σ(openWarehouse.levels) | Руды, газы (сырые), ледяные |
| Переработанный (крытый) | 0.1 + 0.025 × Σ(warehouse.levels) | Чистые элементы (abundant, common), конструкционные материалы |
| Высокотехнологичный (спец) | 0.01 + 0.0025 × Σ(highTechStorage.levels) | Электроника, сверхпроводники, редкие/уникальные элементы |

При переполнении склада соответствующее здание останавливается.

## 2. Система добывающих зданий

Добывающие здания извлекают сырьевые руды из **планетарных пулов** планеты
([31-resources.md](./31-resources.md) §6/§7): наличие месторождения под
конкретной клеткой больше не определяет доступ к ресурсу, положение здания
влияет только на террейн-бонусы, синергию и правила размещения.

> **Контракт добычи (ORE-POOLS-DOCS-01):**
>
> 1. **Один общий бюджет на здание за тик**: `budget_тик = baseRate ×
>    levelMult × terrainMult × synergyMult (× geologicalMult — буровая)`;
>    бюджет рассчитывается ОДИН раз на здание, число видов руды в пулах НЕ
>    умножает пропускную способность.
> 2. **Роли источников — data-driven** (`sourceBuildingId` / `minSourceLevel`
>    ore-каталога, [34-ores.md](./34-ores.md) §3.8); не дублируются
>    отдельными списками.
> 3. **Добытое уменьшает пул** (`remainingQuantity` по ID руды) и добавляется
>    в `planet.resources[oreId]` (склад); при полном складе непомещённый
>    объём не списывается из недр.
> 4. **Распределение бюджета** — детерминированный планировщик «минимумы →
>    пропорциональный излишек» ([35-warehouse-and-logistics.md](./35-warehouse-and-logistics.md) §2.7);
>    ручное назначение руды зданию игроком НЕ предусматривается.

### 2.1 Шахта (Mine)

**Назначение**: добыча совместимых металлических руд из планетарных пулов планеты.

**Доступные ресурсы**: Fe, Ti, Al, Cr, Mn, Ni, Cu, Zn, Sn, Pb, Co, W, Mo, V, Ag, Pt, Au, U, Li, H₂O-ice и другие совместимые руды (по `sourceBuildingId` каталога).

**Формула добычи (бюджет здания за тик):**

```
budget_тик = baseRate × levelMult × terrainMult × synergyMult
```

| Параметр | Описание | Диапазон |
|----------|----------|----------|
| `baseRate` | Базовая скорость добычи | 1.0 ед./день (= 0.001 млрд т) |
| `levelMult` | `1 + уровень × 0.15` | 1.15–2.5 |
| `terrainMult` | Бонус местности гекса здания | см. таблицу terrainBonus каталога |
| `synergyMult` | Синергия mining-cluster соседства | §5 |

> **ORE-POOLS-DOCS-01:** бюджет — общий для всех добываемых руд; доли между
> ними распределяет планировщик (минимумы → пропорциональный излишек,
> [35-warehouse-and-logistics.md](./35-warehouse-and-logistics.md) §2.7).
> `availability` пула — вес доли, а не множитель сверх бюджета.
> Совокупный выпуск здания не растёт от добавления видов руды.
> Историческая формула черновика «`production_rate = availability ×
> mine_level × gravity_bonus × workforce_efficiency`» не реализована и
> superseded бюджетной моделью; гравитационные/рабочие модификаторы
> могут быть добавлены отдельным решением владельца.

**Ограничения**: нельзя строить на газовых гигантах.

### 2.2 Карьер (Quarry)

**Назначение**: добыча совместимых неметаллических ресурсов (Si, O, C, S, P, Ca, Na, K, Mg, `CaCO3`, `NaCl`, `Ba-ore-quarry` и т.д.) из планетарных пулов.

**Доступные ресурсы**: совместимые неметаллические руды и поверхностные соединения по `sourceBuildingId` каталога, включая `H2O-ice`.

**Формула добычи** — та же бюджетная модель, что у шахты (§2.1):

```
budget_тик = baseRate × levelMult × terrainMult × synergyMult
```

> **Отличие от шахты**: набор совместимых пулов (`nonmetal_ore`/
> поверхностные соединения по каталогу); бонус гравитации черновика
> (§2.1) не применяется. Бюджет — общий для всех добываемых руд
> (планировщик — 35 §2.7).

**Ограничения**: нельзя строить на газовых гигантах и чисто ледяных планетах (льда > 90% поверхности).

### 2.3 Газовый экстрактор (Gas Extractor)

**Назначение**: добыча газов из атмосферы планеты (H, He, N, CO₂, CH₄, NH₃, H₂S).

**Доступные ресурсы**: зависит от типа атмосферы.

| Тип атмосферы | Доступные газы | Эффективность |
|---------------|----------------|---------------|
| Нет | — | Строить нельзя |
| Тонкая | CO₂, N | 0.3 |
| Плотная | H, He, N, CO₂, O₂ | 0.7 |
| Токсичная | CO₂, H₂S, SO₂, N, CH₄ | 0.6 |
| Инертная | He, Ne, Ar, N | 0.5 |
| Газовый гигант | H, He, C (в виде CH₄), N | 1.0 |

**Формула добычи** (ед./тик):

```
production_rate = atmospheric_composition × gas_extractor_level × atmosphere_efficiency
```

| Параметр | Описание |
|----------|----------|
| `atmospheric_composition` | Доля нужного газа в атмосфере (0.0–1.0) |
| `gas_extractor_level` | Уровень экстрактора (1–10) |
| `atmosphere_efficiency` | Зависит от типа атмосферы (см. таблицу выше) |

**Ограничения**: **только на планетах с атмосферой**. На планетах без атмосферы здание построить невозможно.

> **ORE-POOLS-DOCS-01:** атмосферная добыча отделена от геологических пулов —
> газовый экстрактор получает источники из атмосферы и НЕ читает/НЕ уменьшает
> планетарные рудные пулы ([31-resources.md](./31-resources.md) §9.3,
> [34-ores.md](./34-ores.md) §3.8.2). Расходы атмосферы не моделируются пулами.

### 2.4 Бурильная установка (Drilling Rig)

**Назначение**: глубокое бурение — доступ к редким элементам, залегающим на глубине.

**Доступные ресурсы**: редкие и уникальные элементы — Ir, Os, Re, Ru, Rh, Pd, Hf, Ta, Nb, Zr, Be, а также геотермальные источники.

**Формула добычи** (ед./тик):

```
production_rate = deep_availability × drill_level × geological_activity_bonus
```

| Параметр | Описание | Диапазон |
|----------|----------|----------|
| `deep_availability` | Доступность редкого элемента в глубоких слоях (0.0–1.0) | Обычно ниже, чем поверхностная |
| `drill_level` | Уровень установки (1–10) | Каждый уровень увеличивает глубину бурения |
| `geological_activity_bonus` | Бонус геологической активности | См. таблицу ниже |

**Бонус геологической активности**:

| Тип планеты | Бонус | Обоснование |
|-------------|-------|-------------|
| Вулканическая | 1.5 | Магма выносит глубинные породы |
| Скалистая | 1.0 | Стандартные условия |
| Океаническая | 0.8 | Бурение через воду сложнее |
| Пустынная | 1.1 | Обнажённые породы |
| Ледяная | 0.6 | Лёд затрудняет бурение |

**Особенность**: на уровнях 1–4 доступна только верхняя мантия (распространённые элементы). Уровни 5–7 открывают нижнюю мантию (редкие элементы). Уровни 8–10 открывают ядро (уникальные элементы).

>    (роль — `sourceBuildingId='drilling_rig'`, порог `minSourceLevel`,
>    [34-ores.md](./34-ores.md) §3.8), привязка залежи к гексу выведена из
>    модели. Исторические п.4–5 описывают механику гекс-модели —
>    superseded (см. [31-resources.md](./31-resources.md) §10.4, §12).

**Ограничения**: нельзя строить на газовых гигантах (слой surface).

### 2.5 Ледодобывающая станция (Ice Harvester)

**Назначение**: добыча воды и замёрзших газов на ледяных планетах, а также на планетах с полярными шапками.

**Доступные ресурсы**: H₂O (вода/лёд), замёрзший CO₂, замёрзший N₂, замёрзший CH₄, NH₃ (аммиачный лёд).

**Формула добычи** (ед./тик):

```
production_rate = ice_availability × harvester_level × temperature_bonus
```

**Бонус температуры** (парадоксально — чем холоднее, тем больше льда):

| Температура поверхности | Бонус | Обоснование |
|------------------------|-------|-------------|
| > 50°C | 0.0 | Лёд отсутствует, строить нельзя |
| 0°C – 50°C | 0.3 | Сезонный лёд / полярные шапки |
| −50°C – 0°C | 0.7 | Многолетний лёд |
| −150°C – −50°C | 1.0 | Сплошной ледяной покров |
| < −150°C | 1.2 | Толстый ледяной панцирь (Европа, Плутон) |

**Ограничения**: можно строить только на планетах со средней температурой ниже +50°C. На более горячих планетах здание недоступно.

### 2.7 Колониальный хаб (Colony Hub) — пассивная добыча (ORE-POOLS-DOCS-01)

**Назначение**: центр колонии; сохраняет задумку **малой пассивной добычи
поверхностных ресурсов** по общепланетарному пулу.

**Контракт:**

1. **Локальная добыча «только под своим гексом» ОТМЕНЕНА** — хаб больше не
   читает залежи под собственной клеткой (гекс-залежи выведены из модели).
2. Хаб получает **малый планетарный бюджет** поверхностной добычи:
   ориентир — **50% базовой скорости шахты** (`0.5 × baseRate`) с текущим
   множителем уровня хаба (`1 + уровень × 0.1`); бюджет — один общий
   на тик, распределение — тем же планировщиком (35 §2.7).
3. **Кандидаты хаба** — только поверхностные mine/quarry-пулы
   (включая `H2O-ice`); **глубинные руды и атмосферные газы хаб НЕ добывает**.
4. Хаб не получает террейн-бонусы добычи и синергию mining-cluster
   (пассивная добыча).
5. Здание хаба на любом гексе не блокируется из-за отсутствия/бедности
   локального депозита — добыча идёт из общепланетарных пулов.

### 3.0 Цеховая модель переработки (processor + construction_materials_plant)

#### 3.0.1 Цех (workshop)

**Единица исполнения партии.** Уровень L processing-здания содержит ровно L
цехов с стабильной нумерацией 1..L. Один цех исполняет **не более одной партии
одновременно**; начатая партия не прерывается (в т.ч. для приоритета
специалиста — правило «на следующей границе партии»). Пропускная способность
здания = количество цехов; отдельный множитель скорости за уровень здания
**отсутствует**. Бонусы синергии соседства (§5) применяются к цехам
surface-экземпляра (смежные шахты +15%, склады +20%).

- **Обычный (plain) цех**: исполняет любую runnable-задачу своего пула с базовой
  эффективностью переработчика (×0.75, чистота 0.78).
- **Цех-специалист**: имеет профиль-рецепт (`specializationRecipeId`) и уровень
  специализации 1–5. На совпадающем рецепте — бонусы §3.0.2; на несовпадающем —
  работает как обычный (fallback, без второго штрафа).

#### 3.0.2 Специализация цеха (необратимая)

**Получение**: на обычном цехе — действие **«Специализировать»** с выбором
**конкретного recipeId** из каталога §3.0.3 (разрешённого для пула здания).
Доступно с уровня здания 1. Цех должен быть свободен (без текущей партии).
Стоимость — `specializeCost` здания; после выбора цех получает
`specializationRecipeId` и уровень 1.

**Необратимость**: снять специализацию, сменить рецепт или понизить уровень
специализации **невозможно**. Удаление цеха понижением уровня здания (§3.0.4)
стирает специализацию и вложения безвозвратно.

**Уровень специализации 1–5**: действие «Улучшить специализацию», стоимость =
`upgradeSpecializationCost × specializationLevel` (существующая механика).
Бонусы: `yieldMult = 1.0 × (1 + 0.02 × (L−1))`, `purity = 0.92 + 0.0175 × (L−1)`
(совпадающий рецепт). На несовпадающем рецепте специалист работает с базовой
эффективностью переработчика (×0.75 / 0.78) — без второго штрафа за несовпадение.

#### 3.0.3 Каталог специализаций цехов (по recipeId)

Каталог data-driven (`src/data/workshop-specializations.ts`): каждая запись —
ID (= recipeId), имя, совместимый пул. Специализация доступна для рецептов,
разрешённых в соответствующем пуле:

| Пул | Здание | Разрешённые рецепты для специализации |
|-----|--------|----------------------------------------|
| Стройматериалы | `construction_materials_plant` | ровно 6 базовых R-27: `smelt_fe`, `smelt_si`, `smelt_al`, `smelt_c`, `smelt_cu`, `smelt_ti` |
| Продвинутый | `processor` | все прочие рецепты пула `processor` (плавка редких/глубинных руд, хим. разложение, лёд, газы) |

Категорийная модель (7 категорий Block 05) остаётся только для предельных форм
`refinery`/`synthesizer` (§3.2/§3.3) и их очередей.

#### 3.0.4 Понижение уровня и удаление цеха

Понижение L→L−1 удаляет именно **цех №L**. Если удалённый цех исполнял партию:
- player-партия возвращается в **хвост FIFO-очереди соответствующего пула** с
  сохранённым прогрессом (оставшиеся тики) — заказ не пересоздаётся и не теряется;
- системная авто-партия R-27 просто прекращается (заказа нет).

Специализация, уровень специализации и вложения удалённого цеха теряются
**безвозвратно**; следующий upgrade создаёт новый обычный цех №L. Снос здания
(уровень 1 → 0) освобождает все его цехи по тем же правилам ре-очереди.

#### 3.0.5 Контракт детерминированного планировщика

Общий компонент для обоих пулов (`src/economy/workshop-scheduler.ts`). Пул =
все цехи всех экземпляров соответствующего здания на планете (surface →
atmosphere → orbit, детерминированный порядок). За тик, по каждому пулу:

1. **Продвижение начатых партий** (без вытеснения): прогресс −= синергия
   экземпляра; энергия — `recipe.energyCost / total` за тик; при отсутствии
   энергии партия стоит (цех удерживается).
2. **Назначение свободным цехам** (порядок детерминирован):
   a. **Приоритет специалиста**: свободный цех-специалист забирает первую
      runnable-задачу своего профиля (player-FIFO → затем авто-кандидат).
   b. **Общий FIFO**: оставшиеся runnable-задачи — свободным обычным цехам и
      специалистам без доступной задачи профиля (специалист временно работает
      как обычный).
   c. **Авто-кандидаты R-27** (только строительный пул): оставшиеся свободные
      цехи заполняются кандидатами в порядке Fe → Si → Al → C → Cu → Ti.
3. **Runnable-гейты** (при назначении): наличие входов (для авто-кандидатов —
   над резервным полом склада), энергия ≥ per-tick, место под ВСЕ выходы
   партии (canStoreResource). Недоступная задача не занимает цех и не
   блокирует доступные (skipped, отображается в очереди с причиной).
   **Брони на тик (v3.0.1 — P1-1/P1-2, аудит Issue #23, 2026-10-29):**
   гейты считаются по остатку свободных ресурсов — вычитаются входы, энергия
   и место под выходы, уже занятые идущими партиями и партиями, назначаемыми
   в этом же тике. Аккумулятор броней один на планету на тик (создаётся
   диспетчером, виден обоим пулам), пересчитывается из состояния партий
   каждый тик, в сейв не сохраняется. Место под выходы считается по
   **фактическому выходу цеха-исполнителя** (§3.0.2: специалист на профильном
   рецепте даёт выше номинала), а не по номиналу рецепта. Две партии, которым
   суммарно не хватает входов/энергии/места, не назначаются вместе —
   назначается первая по порядку, вторая ждёт в очереди.
4. **Завершение партии**: перед списанием/начислением — **повторная проверка**
   (входы целиком; место под фактический выход по типам склада). Если
   ресурсов или места не хватает (параллельная партия забрала входы; место
   занято между назначением и завершением), партия **не завершается силой и
   не удерживает цех**: авто-партия снимается; player-партия возвращается в
   очередь с сохранённым прогрессом (0 тиков работы — досдача в тот же тик,
   когда ресурсы/место появятся), цех освобождается немедленно. Не
   допускаются отрицательные входы и выход сверх вместимости склада. При
   успешном расчёте: списание входов, начисление выходов (формулы §3.0.2 по
   цеху-исполнителю, средневзвешенная чистота); player-партия с
   `repeat=true` возвращается в **хвост** пула (ротация), без repeat —
   удаляется. Одна задача (queue item) никогда не исполняется двумя цехами.

| Плавка глубинных руд | `deep_ore_smelting` (minBuildingLevel 5) | — |
| Переработка льда | `ice_melting` | — |
| Переработка газов | `gas_processing` (minBuildingLevel 4) | — |
| Синтез сплавов и материалов | `alloy_synthesis` | `synthesizer` (§3.3) |

> `refinery` (§3.2) — предустановленная специализированная форма (категория
> `metal_smelting`), строится напрямую после исследования «Высокочистая
> переработка». Категорийная специализация `processor` упразднена (§3.0 v3.0).

### 3.1 Переработчик (Processor)

**ID:** `processor` · **Пул**: продвинутый (уровень L = L цехов, §3.0)

**Концепция**: Здание переработки продвинутых/прочих рецептов (редкие и глубинные руды, химическое разложение, лёд, газы). Уровень L содержит ровно L цехов; один цех — одна партия одновременно (§3.0.1). Базовые строительные рецепты R-27 (Fe/Si/Al/C/Cu/Ti) перенесены на `construction_materials_plant` (§3.6) и этим зданием больше не исполняются.

**Ключевые механики** (цеховая модель v3.0):

- **Пропускная способность** = количество цехов. Уровень L → L параллельных партий.
  Отдельный множитель скорости за уровень здания **отменён** (v2.x — устарело:
  `total_capacity = base_capacity × level`).
- **Разделения ёмкости нет**: каждый цех исполняет ровно одну партию одного
  рецепта; штраф мультирецепта (`1/sqrt(activeRecipes)`, `per_recipe_capacity`)
  к цеховой модели не применяется.
- **Очередь**: продвинутый пул планеты (FIFO + приоритет специалистов, §3.0.5).

**Стратегическое следствие**: игрок увеличивает параллелизм апгрейдами уровня
(новый цех) и строит несколько Переработчиков; цехи специализируются под
конкретные рецепты пула (необратимо, §3.0.2) для высшей чистоты/выхода.

**Чистота продукта**: обычный цех — 0.78 (техническая); цех-специалист на
профильном рецепте — 0.92–0.99 (высшая).

**Разблокировка по уровням** (какие руды вообще доступны для рецептов пула —
уровень ЗДАНИЯ не гейтит рецепты, цехи равноправны):

| Уровни (число цехов) | Что открывает |
|--------|-------------------|
| 1–2 | 1–2 параллельные партии продвинутых рецептов |
| 3–4 | 3–4 параллельные партии; появляется смысл в специализации цехов |
| 5–10 | 5–10 параллельных партий (максимальный параллелизм уровня) |

**Ограничения**: Требует входной ресурс на складе. Не перерабатывает чистые элементы (для этого нужен Синтезатор, см. §3.3).

**Специализация**: цеховая, по конкретному recipeId пула processor (§3.0.2–3.0.3);
необратима. Категорийная специализация здания (Block 05) упразднена.

### 3.2 Очистительный комплекс (Refinery) — предустановленная специализированная форма

**ID:** `refinery` (категорийная модель Block 05 — на цехи НЕ переводился)

**Концепция**: **Предустановленная специализированная форма** переработчика, заточенная под **высокочистую очистку металлов** (категория `metal_smelting`). Производит элементы **ВЫСШЕЙ ЧИСТОТЫ** (0.95–0.99). Строится напрямую после исследования «Высокочистая переработка» (получение специализацией processor упразднено вместе с категорийной моделью §3.0 v3.0).

**Механика**: прежняя категорийная карусель (spec-priority/sticky/carousel R-26) —
рецепты `refine_au`/`refine_pt`/`refine_u` с minSpecializationLevel 5.
- Энергозатраты: **×2** по сравнению с эквивалентным рецептом Переработчика
- Чистота выхода: **0.95–0.99** (у цеховых зданий 0.78 / 0.92+ у специалистов)

**Кому нужен**:
- Электроника (Si, Au чистота ≥ 0.9)
- Сверхпроводники (Y, Ba, Cu чистота ≥ 0.9)
- Ядерное топливо (U чистота ≥ 0.95)

> **Для программиста**: «чистота» элемента — числовой параметр 0.0–1.0. Цеховые здания: обычный цех 0.78, специалист 0.92–0.99. Очистительный комплекс — 0.95–0.99. Завод электроники требует чистоту ≥ 0.9.

### 3.3 Синтезатор (Synthesizer)

**ID:** `synthesizer` (категорийная модель Block 05 — на цехи НЕ переводился)

**Концепция**: Обрабатывает переработку Уровень 1→2 — объединяет чистые элементы в сплавы, материалы и соединения. Это **НЕ** переработчик руд; он синтезирует новые материалы из уже чистых элементов.

**Механика**: прежняя категорийная карусель (R-26), категория `alloy_synthesis`.

**Рецепты**:

- **Сплавы**: Fe(10)+C(3)→Стальной сплав, Ti(8)+Al(4)+V(1)→Титановый сплав, Fe+Cr+Ni→Нержавеющая сталь
- **Органика**: C(5)+H(8)→Пластик, C(8)+H(12)+S(1)→Синтетическое топливо, C(3)+H(4)+N(2)→Композитный материал
- **Кристаллы**: Si(6)→Кремниевый кристалл, C(высш. чистота)→Алмазная подложка
- **Сверхпроводники**: Y(1)+Ba(2)+Cu(3)+O(4)→Сверхпроводник

### 3.5 Цепочки зданий на гекс-сетке

Каждая перерабатывающая линия состоит из **трёх связанных зданий**:

```
[Входное хранилище] → [Здание переработки] → [Выходное хранилище]
```

| Звено цепочки | Здание | Функция |
|---------------|--------|---------|
| Входное хранилище | Планетарный виртуальный склад | Принимает сырьё от добывающих зданий |
| Переработка | Переработчик / Очистительный комплекс / Синтезатор | Превращает сырьё в продукт |
| Выходное хранилище | Планетарный виртуальный склад | Хранит готовый продукт до передачи дальше |

**Правила связи**:
- Здания должны быть соединены **конвейером** или **автотранспортом**
- Если здания **смежны** (соседние гексы), конвейер не нужен — ресурсы передаются мгновенно
- При несмежном размещении требуется логистическая связь (см. раздел 4)

### 3.6 Завод строительных материалов (Construction Materials Plant) — PROC-WORKSHOPS-01

**ID:** `construction_materials_plant` · **Пул**: стройматериалы (уровень L = L цехов, §3.0)

**Концепция**: Отдельное физическое здание (поверхность, уровни 1–10) для шести
базовых рецептов R-27: `smelt_fe`, `smelt_si`, `smelt_al`, `smelt_c`, `smelt_cu`,
`smelt_ti` (10 ед. руды → партия). Эти рецепты перенесены сюда из `processor`;
одновременно старым авто-циклом и новым планировщиком они не исполняются —
единственная исполнительная дорога очередей этого пула.

**Ключевые механики**:

- **Уровень L = L цехов** (§3.0.1); upgrade добавляет обычный цех, понижение
  удаляет цех №L (§3.0.4).
- **Очередь стройматериалов** независима от продвинутого пула processor: задача
  одного пула никогда не занимает цех другого типа. Возможность добавить
  несколько заказов одного рецепта сохраняется; каждая партия потребляет
  свои входные ресурсы.
- **Автоматическое производство R-27** (§11.4): если после распределения
  player-задач остаются свободные цехи, планировщик заполняет их авто-
  кандидатами в порядке приоритета Fe → Si → Al → C → Cu → Ti (входы — над
  резервным полом склада; отсутствующий вход не блокирует готовые задачи).
  Число/объём завершённых партий никогда не превосходит вместимость цехов.
- **Специализация цехов** доступна для шести базовых рецептов (§3.0.2–3.0.3):
  например, цех-специалист `smelt_fe` на железе даёт высшую чистоту/выход;
  при отсутствии железной руды временно работает как обычный (fallback §3.0.5).
- **Показатели** (каталог): энергопотребление 5; стоимость уровня {Fe: 8, Si: 5,
  C: 3}; baseYield 0.75; basePurity 0.78; specializeCost {Fe: 10, Si: 5, Cu: 3};
  upgradeSpecializationCost {Fe: 5, Si: 3, Cu: 2} — та же механика, что у
  processor.

**UI**: карточки цехов 1..L в диалоге здания (статус/профиль/уровень специализации/
текущая партия/прогресс); очереди пула — на вкладке производства планеты,
явно разнесённые с продвинутым пулом (вкладки/секции); видно, какая задача в
FIFO-ожидании, какая выполняется, какая пропускается (нет входов/энергии/места).

## 4. Логистика

> **ВАЖНО**: не переусложнять! Логистика — это автоматическая доставка ресурсов между зданиями. Игрок не управляет каждым грузовиком. Он задаёт связи и приоритеты, система работает сама.

### 4.1 Конвейерная лента (Conveyor)

**Назначение**: связь между зданиями на одной планете по гекс-сетке.

**Характеристики**:

| Параметр | Значение |
|----------|----------|
| Скорость передачи | Мгновенно (в рамках игрового тика) |
| Пропускная способность | 50 ед./тик на уровень конвейера |
| Дальность | Только между **смежными** гексами |
| Стоимость строительства | 5 ед. конструкционных материалов + 1 ед. энергии/тик |
| Уровни | 1–5 |

**Ключевое правило**: конвейер **бесполезен**, если здания не смежные. Он не тянется через несколько гексов. Для связи удалённых зданий используйте автотранспорт.

**Визуализация**: на карте планеты конвейер отображается как линия между двумя гексами.

### 4.2 Автоматический транспорт (Auto-Transport)

**Назначение**: роботизированные грузовики между удалёнными зданиями на одной планете.

**Характеристики**:

| Параметр | Значение |
|----------|----------|
| Скорость доставки | Зависит от расстояния: `delivery_time = distance_hexes × 2` тиков |
| Пропускная способность | 200 ед./рейс |
| Дальность | В пределах планеты (любое расстояние по гекс-сетке) |
| Стоимость строительства | 20 ед. конструкционных материалов + 2 ед. энергии/тик |
| Уровни | 1–3 (определяют количество одновременных рейсов: 1/2/3) |

**Отличие от конвейера**: автотранспорт медленнее (задержка доставки), но работает на любое расстояние.

### 4.3 Склад (Warehouse)

**ID:** `warehouse`

**Концепция**: Планетарный виртуальный склад. Не является хранилищем одного здания — это общая система хранения планеты. Каждое здание-склад на поверхности добавляет +2 500 единиц вместимости за уровень. Colony Hub предоставляет базовую вместимость 10 000 единиц.

**Характеристики**:

| Параметр | Значение |
|----------|----------|
| Базовая вместимость (Colony Hub) | 10 000 ед. |
| Дополнительная вместимость за склад (ур. 1) | +2 500 ед. |
| Формула общей вместимости | `10000 + Σ(2500 × warehouse_level)` для каждого здания склада (затем применяется бонус специализации) |
| Энергопотребление | 1 ед./тик за уровень склада |
| Максимальный уровень | 10 |
| Максимальная вместимость (1 склад ур.10) | 35 000 ед. |

**Механика минимальных резервов**:

Каждый тип ресурса имеет минимальный зарезервированный объём (по умолчанию 50 ед.). Это гарантирует, что один тип ресурса не забьёт весь склад.

```
reservedCapacity = Σ(all minimum reserves)
overflowPool = totalCapacity - reservedCapacity
```

- Ресурсы заполняют минимальные резервы в первую очередь (гарантированное пространство)
- Сверх минимума — ресурсы конкурируют за пул переполнения по приоритету (1-10)
- Если склад полон, добыча ресурса с низким приоритетом приостанавливается

**Настройка резервов**:
- Игрок может настроить минимальный резерв для каждого ресурса (0 = нет гарантии)
- Пресеты по роли колонии: Рудная, Промышленная, Научная, Столица, Своя
- Рудная колония: высокий резерв руд (50), минимальный компонентов (0)
- Промышленная: сбалансированный (20-30)
- Научная: высокий резерв электроники (50), низкий руд (5)
- Игрок может изменить роль или настроить индивидуально в любой момент

**Специализация склада** (сохраняется для бонусов):

| Тип склада | Что хранит (бонус) | Бонус к вместимости |
|------------|-------------------|-------------------|
| Универсальный | Любые ресурсы | ×1.0 (нет бонуса) |
| Рудный | Только сырая руда | ×1.25 (+25% к вместимости) |
| Металлический | Только чистые металлы | ×1.20 (+20% к вместимости) |
| Газовый | Только газы | ×1.20 (+20% к вместимости) |
| Компонентный | Только компоненты | ×1.15 (+15% к вместимости) |

> **Интеграция с BakedGalaxyModel**: классификация ресурсов по категориям (ore/atmospheric/ice/element) определяется через baked-модель галактики. Это обеспечивает корректное сопоставление типа склада с хранимыми ресурсами (например, Fe-ore → ore, H₂O → ice, H₂ → atmospheric).

### 4.4 Орбитальный буфер и космопорт

**Орбитальный буфер** — промежуточное хранилище на орбите планеты для межпланетных перевозок.

**Космопорт (Spaceport)**
- **ID:** `spaceport`
- **Слой:** orbit (орбитальный слот)
- **Назначение:** обеспечение орбитального буфера и погрузки/разгрузки транспортных кораблей
- **Характеристики**:

| Параметр | Значение |
|----------|----------|
| Вместимость орбитального буфера (ур. 1) | 500 ед. |
| Формула вместимости | `500 × spaceport_level` |
| Максимальный уровень | 5 |
| Энергопотребление | 3 ед./тик за уровень |
| Количество одновременных операций | 1 корабль за уровень |

**Механика работы**:
1. Игрок выбирает ресурсы на планетарном складе → «Отправить на орбиту»
2. Ресурсы перемещаются из планетарного склада в орбитальный буфер
3. Орбитальный буфер имеет собственную вместимость (отдельно от планетарного склада)
4. Из орбитального буфера ресурсы отправляются на другие планеты через торговые маршруты
5. Прибытие ресурсов: орбитальный буфер → планетарный склад (если есть место)

> **DOC-AUDIT-01 (2026-10-27):** этот орбитальный буфер — буфер **межпланетной логистики** космопорта.
> Буфер финальной сборки корабельного заказа (сваренный корпус + зарезервированные модули до
> финальной сборки) — **другой, отдельный логический/инвентарный буфер** верфи
> ([55-ship-production-flow.md](./55-ship-production-flow.md) §5 п.7): он не включает межпланетную
> логистику, и физически переиспользовать ёмкость §4.4 под него не предполагается без отдельного
> решения владельца. Не считать эти два хранилища одним и тем же складом.

### 4.5 Очередь приоритетов

Когда ресурс нужен нескольким зданиям одновременно, система использует **очередь приоритетов**.

**Приоритеты по умолчанию** (от высшего к низшему):

| Приоритет | Тип здания | Обоснование |
|-----------|-----------|-------------|
| 1 | Энергетика (электростанции) | Без энергии всё останавливается |
| 2 | Добыча (шахты, карьеры) | Без сырья нечего перерабатывать |
| 3 | Переработка (переработчики, очистительные, синтезаторы) | Промежуточное звено |
| 4 | Производство (заводы компонентов) | Конечный продукт |
| 5 | Верфи | Долгосрочные проекты |
| 6 | Исследование (лаборатории) | Не критично в моменте |

**Настройка**: игрок может переназначить приоритеты для каждого склада индивидуально. Например, если срочно нужен корабль — поднять верфь на приоритет 1.

**Механика**:
1. Склад получает 100 ед. Fe
2. Fe запрошен Переработчиком (приоритет 3) и Заводом компонентов (приоритет 4)
3. Fe сначала отправляется в Переработчик, остаток — на Завод компонентов
4. Если Fe не хватает — Завод компонентов ждёт

### 4.6 Межпланетная логистика

**Назначение**: автоматическая доставка ресурсов между планетами с помощью транспортных кораблей.

**Компоненты**:

| Элемент | Описание |
|---------|----------|
| **Транспортный корабль** | Грузовой корабль с грузовым отсеком. Строится на верфи |
| **Торговый маршрут** | Настройка: откуда → куда, что везти, количество |
| **Точка загрузки** | Орбитальный буфер космопорта на планете-отправителе (см. §4.4) |
| **Точка выгрузки** | Орбитальный буфер космопорта на планете-получателе (см. §4.4) |

**Типы маршрутов**:

| Тип | Описание | Когда используется |
|-----|----------|-------------------|
| **Автоматический** | Система сама создаёт маршруты для обеспечения дефицита | По умолчанию |
| **Настраиваемый** | Игрок задаёт конкретный маршрут с параметрами | Для оптимизации |
| **Экстренный** | Одноразовая доставка, максимальный приоритет | При кризисе |

**Формула времени доставки**:

```
delivery_time_ticks = (distance_between_systems × warp_speed_factor) + orbit_departure_time + orbit_arrival_time
```

| Параметр | Значение |
|----------|----------|
| `distance_between_systems` | Расстояние в парсеках |
| `warp_speed_factor` | Зависит от двигателя: 1 тик/парсек (химический), 0.3 (ионный), 0.1 (варп) |
| `orbit_departure_time` | 10 тиков |
| `orbit_arrival_time` | 10 тиков |

**Космопорт**: здание на орбитальном слоте (уровни 1–5), обеспечивает орбитальный буфер и определяет количество одновременных операций с транспортными кораблями. Подробности — см. §4.4.

## 5. Бонусы смежных зданий (Синергия v2 — типовая)

Смежные здания (расположенные в соседних гексах) дают **бонусы соседства**
(adjacency bonuses). Это стимул планировать застройку и создавать
производственные кластеры.

> **R-SYNERGY v2 (Задача 24)**: здания разделены по **ТИПАМ**
> (генерирующие, добывающие, перерабатывающие и т.п.); для каждого типа —
> свой набор бонусов. **ПОДТИП** = конкретное здание (солнечная станция ≠
> ядерная ЭС, шахта ≠ карьер): разные подтипы одного типа **не дают бонусов
> друг другу**. **R-27 (2026-08-31)**: кросс-типовые правила mine_processor /
> warehouse_production ВОЗВРАЩЕНЫ (жалоба владельца «не могу определить её
> реальное влияние») + добавлено generator_cluster (жалоба «синергия 3-х
> солнечных электростанций не отображается»). Правила data-driven:
> `src/data/buildings/synergy.json` (7 правил).

### 5.1 Таблица бонусов (активные правила)

| Комбинация | Бонус | Условие |
|------------|-------|---------|
| Лаборатория + Лаборатория | **+10%** скорость исследований | Оба здания смежны (кластерный эффект) |
| Электростанция + потребитель | **−5%** энергопотребление получателя | Электростанция смежна с зданием-потребителем (eCon > 0) |
| Электростанция + потребитель | **+5%** выработка энергии ЭС | Электростанция смежна с зданием-потребителем (power_boost) |
| Шахта + Шахта (один подтип) | **+10%** скорость добычи | Оба здания смежны (mining_cluster) |
| Электростанция + Электростанция (один подтип) | **+5%** выработка энергии | Кластер одно-подтиповых ЭС (generator_cluster, R-27) |
| Экстрактор + Переработчик | **+15%** скорость переработки | Переработчик смежен с добывающим зданием (mine_processor, R-27) |
| Склад + Переработчик | **+20%** скорость переработки | Переработчик смежен со складом (warehouse_production, R-27) |

Типы зданий (производные от `category` каталога): `generator` (energy),
`extractor` (extraction), `processor` (processing), `research`,
`storage` (logistics), `production`, `colony`, `military`. Псевдо-тип-роль
`consumer` = любое здание с `energyConsumption > 0` — генераторы не
потребляют, поэтому power_boost/power_grid между ЭС не действуют; НО
**generator_cluster (R-27)** даёт одно-подтиповым ЭС мизерный бонус
выработки (сетевой резерв).

### 5.2 Правила стекания бонусов

Бонусы **стекаются** (stack), но с убывающей отдачей:

- Если здание получает **один** бонус от одного соседа — полная величина
- Если здание получает **два и более** одинаковых бонусов от разных соседей — каждый следующий бонус уменьшается

**Формула стекания**:

```
total_bonus = bonus_1 + (bonus_2 × 0.5) + (bonus_3 × 0.25) + ... + (bonus_n × 0.5^(n-1))
```

**Пример**: шахта окружена тремя шахтами того же подтипа:
```
total_bonus = 0.10 + (0.10 × 0.5) + (0.10 × 0.25) = 0.175 = +17.5% скорости добычи
```

> Без убывающей отдачи было бы +30%, что слишком мощно.

### 5.3 Условия действия бонусов

1. **Оба здания должны быть активны** (не отключены из-за нехватки энергии)
2. **Оба здания должны быть построены** (не в процессе строительства, уровень ≥ 1)
3. **Бонус применяется мгновенно** при появлении смежности
4. **Бонус исчезает** при сносе или отключении одного из зданий
5. **Симметрия пары «ЭС + потребитель»**: потребитель получает −5%
   энергопотребления за каждую смежную электростанцию (power_grid),
   электростанция получает +5% выработки за каждого смежного потребителя
   (power_boost). Генераторы не потребляют энергию → ЭС не бустят друг друга.
6. **Тип получателя определяет метрику**: генератор получает выработку
   (energy_generation), экстрактор — скорость добычи (mining_speed),
   потребитель — снижение энергопотребления (energy_consumption).

### 5.4 Оптимальные конфигурации (спойлер для игрока)

**Научный кластер**:
```
[Лаборатория] [Лаборатория]
[Лаборатория] [Лаборатория]
```
Каждая лаборатория получает +10% от смежных коллег. Ромб 2×2 на гекс-сетке
имеет диагональную смежность → фактический средний буст +16.25%; линия
4 лабораторий — +12.5% (минимальный цикл гексов = 6, «по +15% у каждой»
недостижимы). Агрегат в research_rate — **средний** буст по всем
лабораториям империи (Σ вкладов / Σ лабораторий): изолированные и
слот-лаборатории разбавляют. Действует только на гексах поверхности.

**Горнодобывающий кластер (mining_cluster)**:
```
    [Шахта]
[Шахта] [Шахта] [Шахта]
```
Шахта в центре: +10% +5% +2.5% = **+17.5%** скорости добычи. Важен
ПОДТИП: шахты бустят шахты, карьер шахт не бустит.

**Энергетический узел (power_grid + power_boost)**:
```
[Шахта] [Солнечная станция] [Шахта]
```
Станция получает +5% выработки за каждого смежного потребителя (2 шахты →
+7.5% с затуханием), каждая шахта — −5% энергопотребления.

**Солнечный кластер (generator_cluster, R-27)**:
```
[Солнечная станция] [Солнечная станция]
                 [Солнечная станция]
```
Кластер из 3 одно-подтиповых ЭС: центральная станция (2 смежных) получает
+5% + 2.5% = **+7.5%** выработки, крайние (по 1 смежной) — **+5%**.
Жалоба владельца 2026-08-31 №1 («синергия 3-х солнечных электростанций не
отображается, возможно её и нет») — теперь кластер даёт мизерный, но
реальный бонус выработки и отображается в диалоге здания.

### 5.5 Возвращённые кросс-типовые правила (R-27, 2026-08-31)

Кросс-типовые бонусы (получатель и сосед — разных типов) были отложены в
Задаче 24; **R-27 вернул их по жалобе владельца** («Синергия есть в
описании, не могу определить её реальное влияние», жалоба от 2026-08-31):

| Комбинация | Бонус | Статус |
|------------|-------|--------|
| Шахта + Переработчик | **+15%** скорость переработки | ✅ АКТИВНО (mine_processor) |
| Склад + Производство | **+20%** скорость производства | ✅ АКТИВНО (warehouse_production) |
| Переработчик + Завод компонентов | **+10%** скорость производства | ⏸ отложено (нет здания в каталоге) |

`processing_speed` применяется в `processProductionQueue` (ручная очередь)
и в **авто-переработке** R-27 (§11.4) — бонус реально виден в диалоге
здания (панель «Синергия») и в скорости переработки.

**Очередь строительства**: верфь имеет очередь из модулей для сборки. Каждый модуль собирается за определённое время, зависящее от сложности.

**Формула времени сборки модуля** (⚠️ LEGACY — сборка модулей на верфи; целевая схема выводит
производство модулей на планетарные заводы, см. пометку выше и docs/55 §6):

```
assembly_time_ticks = base_module_time / (shipyard_level × workforce_efficiency × adjacency_bonus)
```

`base_module_time` — базовое время сборки модуля (определяется рецептом модуля).

### 7.2 Орбитальная верфь (Orbital Shipyard)

**Назначение**: верфь, строящая корабли прямо в космосе. Не занимает гекс на поверхности планеты.

> **SHIPFLOW-DOCS (2026-10-27):** в принятой владельцем архитектуре [55-ship-production-flow.md](./55-ship-production-flow.md)
> (подробный документ ожидает приёмки владельца — DOC-AUDIT-01)
> орбитальная верфь выполняет **сварку корпуса из корпусных элементов** и **финальную сборку** из готовых
> модулей; модули и корпусные элементы производятся на планете и передаются в локальный орбитальный
> буфер сборки (внутрипланетный internal transfer). Очередь заказов каждой верфи — последовательная
> (один активный ship build project), отмена невозможна с начала FINAL_ASSEMBLY (docs/55 §8, §11–§12).
> Концепция локальных буферов и per-planet логистической границы — docs/55 §5.

**Отличия от планетарной верфи**:

| Параметр | Планетарная верфь | Орбитальная верфь |
|----------|-------------------|-------------------|
| Расположение | Гекс на планете | Орбита планеты |
| Стоимость строительства | Дешевле | Дороже (×2 ресурсы) |
| Доступные размеры | Ограничены уровнем | +1 уровень эквивалента (ур. 5 = средние + лёгкий тяжёлый) |
| Время сборки | Базовое | −20% (нет гравитационных ограничений) |
| Требование | Нет | Космопорт ур. 3+, Инженерия 4 |
| Максимальное количество | 1 на планете | Зависит от размера орбиты (1–3) |

**Построение орбитальной верфи**:
1. На планетарной верфи (ур. 4+) собираются секции орбитальной верфи
2. Секции запускаются на орбиту (10 тиков на секцию)
3. Секции собираются в орбитальную верфь (занимает 100 тиков)

**Ограничение**: орбитальная верфь не может строить другую орбитальную верфь.

## 8. Энергетика

Электростанции — единственный источник энергии. Без энергии все здания останавливаются.

### 8.1 Солнечная станция (Solar Plant)

**Назначение**: выработка энергии из звёздного излучения.

**Формула мощности** (ед./тик):

```
power_output = base_output × solar_station_level × star_luminosity / distance_factor
```

| Параметр | Описание | Диапазон |
|----------|----------|----------|
| `base_output` | Базовая мощность | 10 ед./тик |
| `solar_station_level` | Уровень станции (1–10) | Целое число |
| `star_luminosity` | Светимость звезды | 0.01 (красный карлик) – 10 000 (голубой гигант) |
| `distance_factor` | Квадрат расстояния от звезды | `distance_au²` |

**Эффективность по типу звезды** (на расстоянии 1 АЕ):

| Тип звезды | Светимость | Мощность станции ур. 1 |
|------------|-----------|----------------------|
| Красный карлик (M) | 0.01 | 0.1 ед./тик |
| Жёлтый карлик (G) | 1.0 | 10 ед./тик |
| Белый карлик | 0.01 | 0.1 ед./тик |
| Красный гигант | 100 | 1 000 ед./тик |
| Голубой гигант | 10 000 | 100 000 ед./тик |

**Ограничения**: не работает на планетах без солнечного освещения (глубокие подземелья, обратная сторона приливно-захваченных планет). Эффективность снижается на планетах с плотной атмосферой (−20%).

### 8.2 Ядерный реактор (Nuclear Reactor)

**Назначение**: постоянная мощность, потребляет U (уран) или Th (торий).

**Характеристики**:

| Параметр | Значение |
|----------|----------|
| Базовая мощность (ур. 1) | 50 ед./тик |
| Максимальная мощность (ур. 10) | 500 ед./тик |
| Формула мощности | `50 × reactor_level` |
| Расход топлива | `0.01 × reactor_level` ед. U/Th за тик |
| Тип топлива | U или Th |

**Преимущества**: постоянная мощность, не зависит от расстояния до звезды, работает на любой планете.

**Недостатки**: потребляет редкое топливо (U, Th), риск аварии (см. ниже).

**Риск аварии**: при уровне выше 7 и износе > 80% — шанс аварии 0.01% за тик. Авария выводит реактор из строя на 200 тиков и наносит урон смежным зданиям.

### 8.3 Термоядерный реактор (Fusion Reactor)

**Назначение**: высокая мощность, потребляет H (водород), D (дейтерий), T (тритий).

**Характеристики**:

| Параметр | Значение |
|----------|----------|
| Базовая мощность (ур. 1) | 200 ед./тик |
| Максимальная мощность (ур. 10) | 2 000 ед./тик |
| Формула мощности | `200 × reactor_level` |
| Расход топлива | `0.1 × reactor_level` ед. H/D/T за тик |
| Тип топлива | H, D (дейтерий), T (тритий) — чем тяжелее, тем мощнее |

**Модификаторы топлива**:

| Топливо | Бонус к мощности |
|---------|-----------------|
| H (водород) | ×1.0 |
| D (дейтерий) | ×1.5 |
| T (тритий) | ×2.0 |
| D+T смесь | ×3.0 |

**Требование**: технология «Термоядерный синтез» (уровень 1 для постройки, уровень 2 для ур. 4+, уровень 3 для ур. 7+).

**Преимущества**: в 4 раза мощнее ядерного, топливо распространено (H есть везде).

**Недостатки**: дорого в строительстве, требует высокую технологию.

### 8.4 Геотермальная станция (Geothermal Plant)

**Назначение**: дешёвая энергия из недр планеты.

**Характеристики**:

| Параметр | Значение |
|----------|----------|
| Базовая мощность (ур. 1) | 80 ед./тик |
| Максимальная мощность (ур. 10) | 800 ед./тик |
| Формула мощности | `80 × plant_level × geological_activity` |
| Расход топлива | Нет |
| Энергопотребление | 0 |

**Модификатор геологической активности**:

| Тип планеты | geological_activity | Можно строить? |
|-------------|---------------------|----------------|
| Вулканическая | 1.5 | Да (идеально) |
| Скалистая (тектонически активная) | 1.0 | Да |
| Океаническая | 0.8 | Да |
| Скалистая (тектонически неактивная) | 0.4 | Да, но слабо |
| Пустынная | 0.5 | Да |
| Ледяная | 0.1 | Нет (недостаточно тепла) |
| Газовый гигант | 0.0 | Нет |

**Ограничение**: **только на тектонически активных планетах**. На ледяных планетах и газовых гигантах строить нельзя.

**Преимущества**: бесплатное топливо, дешёвое строительство.

**Недостатки**: ограничена типом планеты, мощность ниже термоядерной.

### 8.5 Антиматериальный реактор (Antimatter Reactor)

**Назначение**: эндгейм — максимальная мощность.

**Характеристики**:

| Параметр | Значение |
|----------|----------|
| Базовая мощность (ур. 1) | 1 000 ед./тик |
| Максимальная мощность (ур. 10) | 10 000 ед./тик |
| Формула мощности | `1 000 × reactor_level` |
| Расход топлива | `0.001 × reactor_level` ед. антиматерии за тик |
| Тип топлива | Антиматерия (производится на спец. установке) |

**Требование**: технология «Антиматерия» (уровень 1 для постройки, уровень 2 для ур. 5+, уровень 3 для ур. 8+).

**Производство антиматерии**: требуется «Генератор антиматерии» (отдельное здание, строится только при наличии технологии «Антиматерия» ур. 2+). Выработка: 0.01 ед. антиматерии/тик при ур. 1. Потребляет 500 ед. энергии/тик (парадокс — нужно много энергии, чтобы создать антиматерию).

**Риск аварии**: при уровне выше 5 и износе > 80% — шанс аварии 0.05% за тик. Авария уничтожает реактор и наносит тяжёлый урон всем зданиям в радиусе 3 гексов.

**Преимущества**: абсолютный максимум мощности.

**Недостатки**: крайне дорогой в производстве и эксплуатации, высокий риск аварии, требует редчайшую технологию.

## 9. Система уровней зданий

### 9.1 Общие правила

- Все здания имеют **уровни от 1 до 10**
- Повышение уровня — это **модернизация** существующего здания (не снос и перестройка)
- Модернизация занимает время и требует ресурсы
- Время модернизации: `upgrade_time = base_build_time × level` тиков

### 9.2 Стоимость модернизации

Формула стоимости ресурсов для улучшения с уровня N до N+1:

```
upgrade_cost(resource) = base_cost(resource) × N × 1.2
```

Где `base_cost` — стоимость постройки здания уровня 1.

**Пример**: Шахта уровня 1 стоит 20 Fe, 10 Si. Улучшение до уровня 3:
```
уровень 1→2: (20 × 1 × 1.2) Fe + (10 × 1 × 1.2) Si = 24 Fe + 12 Si
уровень 2→3: (20 × 2 × 1.2) Fe + (10 × 2 × 1.2) Si = 48 Fe + 24 Si
```

### 9.3 Эффекты уровней

| Уровень | Скорость работы | Энергопотребление /ед. | Вместимость (склад) | Доступные рецепты |
|---------|-----------------|------------------------|---------------------|-------------------|
| 1 | ×1.0 | ×1.0 | ×1 | Базовые |
| 2 | ×1.2 | ×0.95 | ×2 | +1 рецепт |
| 3 | ×1.5 | ×0.90 | ×3 | +1 рецепт |
| 4 | ×1.8 | ×0.85 | ×4 | +1 рецепт |
| 5 | ×2.2 | ×0.80 | ×5 | +2 рецепта |
| 6 | ×2.7 | ×0.75 | ×6 | +1 рецепт |
| 7 | ×3.2 | ×0.70 | ×7 | +1 рецепт |
| 8 | ×3.8 | ×0.65 | ×8 | +2 рецепта |
| 9 | ×4.5 | ×0.60 | ×9 | +1 рецепт |
| 10 | ×5.0 | ×0.55 | ×10 | +1 рецепт |

**Формула скорости работы**:
```
work_speed = base_speed × level_multiplier(level)
```

**Формула энергоэффективности**:
```
energy_per_unit = base_energy × energy_multiplier(level)
```

> Энергоэффективность означает, что на высоких уровнях здание тратит меньше энергии на единицу продукции. Общее потребление энергии растёт (здание работает быстрее), но удельное — падает.

### 9.4 Потери при переработке

Уровень перерабатывающего здания также влияет на **коэффициент выхода** (yield):

| Уровень | Yield (переработчик) | Yield (очистительный комплекс) |
|---------|---------------------|-------------------------------|
| 1 | 0.60 | 0.450 |
| 2 | 0.63 | 0.455 |
| 3 | 0.66 | 0.460 |
| 4 | 0.69 | 0.465 |
| 5 | 0.72 | 0.470 |
| 6 | 0.75 | 0.475 |
| 7 | 0.78 | 0.480 |
| 8 | 0.81 | 0.485 |
| 9 | 0.84 | 0.490 |
| 10 | 0.85 | 0.500 |

**Формула yield для переработчика**:
```
yield = 0.60 + 0.03 × (level - 1)   (максимум 0.85 на уровне 10)
```

**Формула yield для очистительного комплекса**:
```
yield = 0.450 + 0.005 × (level - 1)   (максимум 0.500 на уровне 10)
```

> Очистительный комплекс на уровне 10 даёт 50% чистого элемента из руды высшей чистоты — это лучше, чем переработчик (85% технической чистоты), когда нужна высшая чистота.

### 9.5 Понижение уровня и снос (R-DEMOLISH)

Обратные операции к модернизации — **для освобождения гекса/слота**:

**Понижение уровня** (`downgradeBuilding`, UI: «Понизить до ур. N»):
- Уровень L → L−1; возврат **50%** стоимости уровня L (`base × (L−1) × 0.5`).
- При L = 1 понижение превращается в **полный снос** (уровень 0 = нет здания).
- Энергобаланс пересчитывается мгновенно.

**Полный снос** (`demolishBuilding`, UI: «Снести здание»):
- Гекс/слот освобождается; специализация и активные рецепты сбрасываются.
- Возврат **50% суммарных вложенных ресурсов**. Модель стоимости
  (симметрична апгрейду): уровень 1 = `base × 1`, уровень i ≥ 2 = `base × (i−1)`
  → суммарно до уровня L: `base × (1 + L(L−1)/2)`.
- **Пример**: лаборатория L3 (base 30 Fe): вложено 30 × 4 = 120 Fe → возврат 60 Fe.

**Правила**:
- **Колониальный хаб нельзя понижать/сносить** (ядро колонии).
- Поддержаны все слои: поверхность (гекс), атмосферный и орбитальный слоты
  (space — нет планетарных слотов).
- События: `economy:building-downgraded` / `economy:building-demolished`.
- MVP-упрощение: снос не блокируется активной очередью производства
  (рецепты ссылаются на buildingId, не на экземпляр).

**Подтверждение сноса (R-24, Задача 24 — запрос владельца)**:
- Любой снос требует подтверждения: «Вы действительно хотите снести
  здание?» (AlertDialog).
- При уровне здания > 1 — **дополнительный** второй вопрос: «Здание выше
  1-го уровня, вы действительно хотите его снести» (двухшаговый поток:
  общий вопрос → вопрос про уровень → снос).
- Понижение уровня при L > 1 подтверждения не требует (обратимая операция).

| Компоненты | 14.0 ед./тик | 70 ед./тик | 14.0 × 0.55 = 7.7 |
| Корабли | 25 ед./тик | 125 ед./тик | 25 × 0.55 = 13.75 |
| Логистика | 2.3 ед./тик | 11.5 ед./тик | 2.3 × 0.55 = 1.27 |
| Наука | 10 ед./тик | 50 ед./тик | 10 × 0.55 = 5.5 |

> **Балансировочное правило**: суммарное энергопотребление всех зданий на планете не должно превышать суммарную выработку. Если превышает — здания с низшим приоритетом отключаются.

## 11. Формулы и расчёты

> ⚠️ **Версия 3.0-draft**: формулы обновлены под шкалу «млрд тонн» и раздельную систему складов.
> **Единица измерения в коде:** 1 ед. = 1 млн т = 0.001 млрд т. См. §1.5.

### 11.1 Базовые константы (TypeScript)

```typescript
// Шкала: 1 ед. = 1 млн т = 0.001 млрд т

// Скорости (ед./день, эквивалент млрд т/день × 1000)
export const BASE_EXTRACTION_RATE = 1.0;      // шахта, карьер, газовый экстрактор (1 ед/день = 0.001 млрд т/день)
export const BASE_PROCESSING_RATE = 2.0;      // processor, synthesizer, refinery (2 ед/день = 0.002 млрд т/день)
export const BASE_PRODUCTION_RATE = 0.1;      // верфь, завод (0.1 ед/день = 0.0001 млрд т/день)

// Вместимость складов (ед.)
export const ORE_WAREHOUSE_BASE = 1000;        // рудный склад (1 млрд т)
export const ORE_WAREHOUSE_PER_LEVEL = 250;    // +0.25 млрд т/ур.
export const PROCESSED_WAREHOUSE_BASE = 100;   // переработанный склад (0.1 млрд т)
export const PROCESSED_WAREHOUSE_PER_LEVEL = 25; // +0.025 млрд т/ур.
export const HIGH_TECH_STORAGE_BASE = 10;      // высокотехнологичный склад (0.01 млрд т)
export const HIGH_TECH_STORAGE_PER_LEVEL = 2.5; // +0.0025 млрд т/ур.
export const ORBIT_BUFFER_PER_LEVEL = 5;       // +0.005 млрд т/ур. (космопорт)

// Множители уровня
export const EXTRACTION_LEVEL_MULT = 0.15;     // 1 + level × 0.15
export const PROCESSING_LEVEL_MULT = 0.15;
export const PRODUCTION_LEVEL_MULT = 0.15;
export const ENERGY_LEVEL_MULT = 0.20;
```

### 11.2 Полная формула добычи (бюджетная модель, ORE-POOLS-DOCS-01)

```
budget_тик = BASE_EXTRACTION_RATE × levelMult × terrainMult × synergyMult (× geologicalMult — drilling_rig)
доля_руды_i = бюджет, распределённый планировщиком между кандидатами здания
            (фаза A: недовыполненные минимумы; фаза B: пропорционально
             remainingQuantity × availability пулов — 35 §2.7)
```

Где:
- `BASE_EXTRACTION_RATE = 1.0 ед./день` (= 0.001 млрд т/день); colony_hub — 0.5 (§2.7)
- `levelMult = 1 + level × 0.15`
- `terrainMult` — бонус местности гекса здания (1.0–1.5)
- `synergyMult` — синергия mining-cluster (§5)
- `geologicalMult` — геологический множитель типа планеты — только буровая, ровно один раз
- `availability` — вес пула (нормализуемый), НЕ множитель сверх бюджета

**Инварианты:**
- Сумма долей одного здания за тик ≤ `budget_тик` (число руд не умножает выпуск).
- Извлечённый объём уменьшает `remainingQuantity` пулов и попадает в склад
  только в реально помещённом объёме (`canStoreResource`).

**Пример:** Шахта ур.5, mountains (×1.5), без синергии:
```
budget = 1.0 × (1 + 5×0.15) × 1.5 = 1.875 ед./день = 0.001875 млрд т/день
```
Этот бюджет делится между всеми совместимыми пулами (например, один пул Fe
и один пул Cu с весами 3:1 → ~1.406 и ~0.469 ед./день), а не выдаётся
каждой руде отдельно.

### 11.3 Формула переработки (цеховая модель, PROC-WORKSHOPS-01)

```
пропускная способность здания = количество цехов = уровень L
скорость партии = recipe.time тиков × (1 / Синергия processing_speed)
```

Где:
- Уровень L содержит ровно L цехов; один цех — одна партия одновременно.
- **Множитель скорости за уровень здания ОТМЕНЁН** (v2.x `levelMult = 1 +
  level × 0.15` и `PROCESSING_LEVEL_MULT` к переработке больше не применяются;
  константа осталась только для добычи/производства).
- Синергия соседства (§5.5: смежная шахта +15%, склад +20%) — единственный
  ускоритель партии; применяется к цехам surface-экземпляра.

**Пример:** Переработчик ур.3 (3 цеха), 3 runnable-задачи → 3 параллельные
партии, каждая за `recipe.time` тиков; ур.5 с 5 задачами — 5 партий.

**Выход партии** — по цеху-исполнителю (§3.0 IMPLEMENTATION NOTE):
обычный цех/фолбэк — ×0.75 (baseYield), чистота 0.78; специалист на
профильном рецепте — ×(1 + 0.02×(Lspec−1)), чистота 0.92–0.99.

### 11.4 Авто-переработка базовых строительных ресурсов (R-27 → PROC-WORKSHOPS-01)

Жалоба владельца 2026-08-31: «при наличии 3-х переработчиков не меняется
количество кремния, железа» — переработка была только через ручную очередь.
R-27 добавил шаг тика `processAutoProcessing`; **PROC-WORKSHOPS-01 (2026-10-28)
заменил его авто-кандидатами детерминированного планировщика строительного
пула** (§3.0.5–3.0.6) — старый обходной цикл удалён (не может оставаться
второй исполнительной дорогой):

**Что перерабатывается автоматически** — базовые строительные руды (шесть
рецептов R-27, приоритет Fe → Si → Al → C → Cu → Ti; данные
`src/data/auto-processing.ts` → `BASE_CONSTRUCTION_RECIPE_IDS`). Рецепты
принадлежат зданию `construction_materials_plant` (§3.6).

**Как**:
- после распределения player-задач строительного пула свободные цехи завода
  заполняются авто-кандидатами (по одному на цех) в порядке приоритета;
- авто-кандидат runnable ⇔ входы есть НАД резервным полом `reserves.minimum`,
  энергия ≥ per-tick, все выходы партии влезают (canStoreResource);
- отсутствующий вход просто пропускает кандидата — готовые задачи не
  блокируются (равноприоритетный выбор продолжает список);
- авто-партия — обычная партия планировщика (`WorkshopBatch` с
  `queueItemId: null`): тратит `recipe.energyCost / total` за тик, завершается
  по тем же формулам выхода; несколько заказов одного рецепта (player) и
  авто-кандидаты потребляют входные ресурсы по отдельности;
- итоговое число/объём завершённых партий ≤ вместимость цехов завода —
  автоматическое производство полностью подчинено конечной ёмкости.

**Ограничения** (как прежде):
- входы авто-кандидатов не расходуются ниже резерва `reserves.minimum` руды;
- выходы — через `canStoreResource` (ёмкость склада + долг резервов §35-1.4);
- энергия — per-tick гейт партии (постоянное потребление зданий уже в
  `recalcEnergyBalance`).

Чистый выход записывается в `resourcePurity` (средневзвешенно, как у
player-партий). Ручная очередь строительного пула работает через тот же
планировщик — отдельной дороги нет.

### 11.5 Формула производства (верфь)

```
production_rate = BASE_PRODUCTION_RATE × levelMult
```

Где:
- `BASE_PRODUCTION_RATE = 0.1 ед./день` (= 0.0001 млрд т/день)
- `levelMult = 1 + level × 0.15`

**Пример:** Верфь ур.5:
```
rate = 0.1 × (1 + 5×0.15) = 0.175 ед./день = 0.000175 млрд т/день
```

### 11.6 Энергобаланс

> Нумерация исправлена DOC-AUDIT-01 (Issue #14): ранее этот раздел дублировал номер §11.5
> («Формула производства (верфь)»); содержание формул не менялось.

```
energyBalance = Σ(production) − Σ(consumption)
```

**Производство:**
- Solar: `10 × levelMult × starLuminosity / orbitalRadius` (орбита: ×1.2)
- Nuclear: `25 × levelMult`
- Colony Hub: `5 × levelMult`

**Потребление:** `buildingDef.energyConsumption × levelMult`

Где `levelMult = 1 + level × 0.20` для энергии.

### 11.7 Формула стоимости строительства

```
build_cost(resource) = costPerLevel(resource) × (1 + 0.2 × (level - 1))
build_time_ticks = baseProductionTime × level
```

**Пример:** Шахта ур.3 (costPerLevel: { Fe: 5, Si: 3 }):
```
cost = { Fe: 5 × (1 + 0.2×2) = 7, Si: 3 × (1 + 0.2×2) = 4.2 }
     = { Fe: 7 ед. = 0.007 млрд т, Si: 4.2 ед. = 0.0042 млрд т }
```

### 11.8 Раздельная система складов (вместимость)

```
oreCapacity = ORE_WAREHOUSE_BASE + ORE_WAREHOUSE_PER_LEVEL × Σ(open_warehouse.levels)
processedCapacity = PROCESSED_WAREHOUSE_BASE + PROCESSED_WAREHOUSE_PER_LEVEL × Σ(warehouse.levels)
highTechCapacity = HIGH_TECH_STORAGE_BASE + HIGH_TECH_STORAGE_PER_LEVEL × Σ(high_tech_storage.levels)
orbitBufferCapacity = ORBIT_BUFFER_PER_LEVEL × Σ(spaceport.levels)
```

**Пример:** Планета с 1 warehouse ур.3 и 1 open_warehouse ур.2:
```
oreCapacity = 1000 + 250×2 = 1500 ед. = 1.5 млрд т
processedCapacity = 100 + 25×3 = 175 ед. = 0.175 млрд т
highTechCapacity = 10 ед. = 0.01 млрд т (нет high_tech_storage)
```

```
При попытке добавить ресурс на склад:

    if (oreUsed + amount > oreCapacity) {
      amount = oreCapacity - oreUsed  // остаток теряется или блокирует добычу
      if (amount <= 0) stopExtraction()
    }
  }
  // аналогично для processed и high_tech
```

```
wear_per_tick = 0.001 (базовый износ)
```

При прочности < 30% — штраф −50% скорости. При 0% — остановка. Ремонт: 10% от стоимости, восстанавливает 25%.
