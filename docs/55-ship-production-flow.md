## 1. Принятые продуктовые решения владельца

**`[OWNER-DECISION]`** — весь раздел. Зафиксировано в Issue #13 (включая ADDENDUM 2026-10-27 — новейший и приоритетный контракт).
Источники каждого решения — тело Issue #13 или его ADDENDUM (уровень доказательности — owner-issue-body):

1. Существующую спецификацию не ломать; готовые разделы переработки (docs/40 §3) не заменять.
   Новое — добавлять, текущую очередь верфи — минимально модернизировать.
2. Сохранить специализированные производства docs/40: §6.1 завод электроники, §6.2 завод двигателей,
   §6.3 завод оружия, §6.4 завод щитов.
3. §6.5 — завод **корпусных элементов/панелей и бронеплит**. Он **не** выпускает готовый корабельный
   корпус: корпус сваривается на верфи из корпусных элементов.
4. Добавить отдельный **универсальный завод комплектующих**: умеет производить **любой ShipModule**,
   включая модули профильных линий. До появления профильного завода на этой планете разрешён
   универсальный маршрут со штрафом 90% производительности; после появления профильного завода рецепт
   универсального завода блокируется для новых постановок/стартов. Это **другое производство и другой
   ID** — не путать с существующим `processor` / универсальным переработчиком (docs/40 §3).
5. Сборка готового корабля — на орбитальной/космической верфи: сварка корпуса из корпусных элементов
   и финальная сборка из готовых модулей. Производство модулей на поверхности и подготовка корпусных
   элементов могут идти одновременно.
6. Длительность одного изделия **не делится** на количество цехов: каждый цех делает своё изделие
   целиком; множество независимых изделий выполняются одновременно (в одном тике — детерминированный
   прогресс нескольких работ).
7. Владелец выразил **предпочтение** арифметическому линейному росту числа цехов W(L)=L. По
   формулировке «предпочтение» (не «утверждаю») линейная модель трактуется как **рекомендуемая
   базовая модель** (§16.4), а не как окончательно зафиксированное решение — финальное закрепление
   W(L) происходит вместе с баланс-пассом новых заводов (§21, вопросы 1/10). Квадратичные
   альтернативы — **вторичные**, посчитаны до уровня 10 только для оценки цены этой альтернативы (§16).
8. (ADDENDUM) Последовательная очередь верфей: **не более одного активного ship build project на одну
   верфь**; детали более поздних заказов не производятся заранее — только когда заказ стал текущим (§8).
9. (ADDENDUM) Межпланетной логистики в срезе нет; буферы и резервы — строго per-planet (§5).

## 2. Термины и модель сущностей

| Термин | Значение |
|---|---|
| **ShipDesign** | Чертёж (docs/50 §1.4, `src/core/types.ts ShipDesign`). **Не** физический инвентарь. Хранится в `GameState.shipDesigns`, переиспользуем. |
| **Build order (заказ)** | Конкретный заказ на постройку одного корабля из дизайна на конкретной верфи. Фиксирует состав заказа (см. §8) и живёт в собственном состоянии (§4). |
| **Module job (задача модуля)** | Задача производства **одного экземпляра** ShipModule для конкретного заказа. Один элемент `moduleIds` = одна задача; одинаковые moduleId **не схлопывать**. Стабильный ID задачи = `orderId + index + moduleId`. |
| **Hull welding (сварка корпуса)** | Операция верфи: корпус сваривается из корпусных элементов (продукция §6.5). |
| **Final assembly (финальная сборка)** | Операция верфи: соединение готового корпуса и всех требуемых модулей в Ship. |
| **Цех (workshop)** | Единица параллельной вместимости завода. Один цех одновременно обрабатывает ≤ 1 изделие и не становится быстрее от добавления цехов. Завод уровня L имеет W(L) цехов (§16). |
| **Буфер компонентов планеты** | Локальное хранилище готовых компонентов/модулей планеты (per-planet). |
| **Буфер сборки верфи** | Орбитальное хранилище верфи: сваренный корпус + зарезервированные модули, ожидающие final assembly (per-planet/per-shipyard). **Отдельный** логический/инвентарный буфер — не орбитальный буфер космопорта docs/40 §4.4 (см. §5 п.7). |
| **Резерв (reserve)** | Связка «физическое изделие ↔ buildOrderId» в ledger; резерв не виден другим заказам (§9). |
| **Ledger** | Единый учёт местоположения каждого физического изделия: `free_stock | reserved_for_order | in_progress_output | assembly_buffer | installed_on_ship`. |

## 4. Стабильная схема конвейера (state machine заказа)

```
DESIGN_VALIDATED → BUILD_ORDER_CREATED → (HULL_WELDING || MODULE_JOBS_QUEUED/RUNNING)
      → HULL_READY + ALL_REQUIRED_MODULES_READY → ORBITAL_FINAL_ASSEMBLY → LAUNCHED_TO_ORBIT
```

**Статусы заказа (предлагаемый enum, durable, сериализуемый):**

| Статус | Смысл | Переходы |
|---|---|---|
| `DESIGN_VALIDATED` | Дизайн прошёл `validateShip` (docs/50 Прил. B), состав заказа зафиксирован (§8) | → `BUILD_ORDER_CREATED` |
| `BUILD_ORDER_CREATED` | Заказ создан, стоит в очереди верфи; задачи НЕ создаются, резерва НЕТ | → `ACTIVE` (когда стал головой очереди) |
| `ACTIVE` | Заказ — текущий на верфи: атомарный reserve выполнен, недостающее оформлено в demand, задачи созданы (ровно один раз) | содержит параллельные операции `HULL_WELDING` и `MODULE_JOBS_QUEUED/RUNNING` |
| `READY_FOR_ASSEMBLY` | `HULL_READY` **и** `ALL_REQUIRED_MODULES_READY` (все физически в буфере сборки, зарезервированы за orderId) | → `FINAL_ASSEMBLY` |
| `FINAL_ASSEMBLY` | Финальная сборка идёт; заказ **не отменяем** (явный отказ API, без мутаций) | → `LAUNCHED_TO_ORBIT` |
| `LAUNCHED_TO_ORBIT` | Ровно один новый Ship на орбите планеты; заказ завершён (терминальный) | — |
| `CANCEL_REQUESTED` / `DRAINING` | Отмена до FINAL_ASSEMBLY: новые работы запрещены, активные доработывают, готовое — на склад (§11) | → `CANCELLED` (терминальный) |
| `CANCELLED` | Терминальный; все резервы освобождены, disposition «вернуть на склад» применён | — |

**Статусы задачи модуля (предлагаемый enum):** `QUEUED → RUNNING → COMPLETED`; особый
`BLOCKED_BY_SPECIALIZED_FACTORY` (не стартует, не удаляется автоматически — §7); для задач отменённого
заказа, завершившихся после отмены — disposition `RETURN_TO_STOCK`.

**Ключевые свойства схемы:**

- Сварка корпуса и изготовление модулей — **независимые** ветки: идут параллельно (в смысле
  детерминированного прогресса нескольких работ в одном тике, §13). Общее время заказа =
  **критический путь**: момент готовности последнего из требуемых компонентов/корпуса + final assembly,
  а **не** сумма длительностей всех независимых задач.
- Каждый элемент `moduleIds` заказа создаёт **отдельную** задачу со стабильным ID
  (`orderId + index + moduleId`); одинаковые moduleId не схлопываются — у каждого экземпляра свой
  прогресс, своё резервирование и свой результат.
- Симуляция однопоточная: «параллельно» = несколько независимых работ продвигаются в одном тике,
  с единым порядком резервирования ресурсов и одним авторитетным `commitState` (Pattern A,
  `mediator.commitState`). **Web Workers не вводятся.**
- MVP: одна планета + её орбитальная верфь; автоматическая внутренняя передача готовых компонентов
  из заводского контура в буфер сборки (§5).

## 5. Буферы и логистическая граница MVP

1. У каждой планеты — собственные **буфер строительных материалов/компонентов** и **буфер сборки
   кораблей на её орбитальной верфи**. Данные/резервы одной планеты **не доступны** другой планете
   (facility lookup строго scoped to planet ID — §15, риск 13).
   **[OWNER-DECISION] Перечень per-planet изолированных сущностей (уточнено DOC-AUDIT-01):**
   компонентный склад (stock), резервы (reserve ledger, §9), блокировка универсальных рецептов
   (factory lock, §7.3), производственный demand активного заказа (§8.2) и буфер сборки верфи —
   **все пять** контуров изолированы по планетам и не разделяются между планетами.
2. **Межпланетной логистики в срезе нет.** Транспортные корабли и межпланетная доставка будут
   проектироваться отдельно, без заранее выдуманных маршрутов, объёмов/скоростей и стоимости
   (docs/40 §4.6 остаётся концепцией).
3. Внутрипланетная передача завершённых компонентов из заводского контура в буфер сборки/склад —
   **internal transfer**, не межпланетная логистика. MVP: автоматическая внутренняя передача.
4. Модель ledger запрещает изделию находиться в двух местах: каждое физическое изделие имеет ровно
   одно место/владение — `free_stock`, `reserved_for_order`, `in_progress_output`, `assembly_buffer`
   либо `installed_on_ship` (§9).
5. Хранение готовых изделий — **по количеству** per component/module ID, если gameplay-семантика
   не требует индивидуального condition/quality/unique ID. Если индивидуальная сущность понадобится —
   это фиксируется как cost/complexity risk отдельным решением, молча не решается (§21).
6. Переполнение хранилища при завершении задачи **не может потерять изделие**: заранее резервируется
   output capacity, либо завершённый output остаётся в durable output-slot цеха до появления места
   (§15, риск 8). Молча выбрасывать изделие или повторять completion запрещено.
7. **Два разных орбитальных хранилища — не одно и то же (уточнено DOC-AUDIT-01).** Орбитальный буфер
   космопорта (docs/40 §4.4) — буфер **межпланетной логистики** (погрузка/разгрузка транспортных
   кораблей, торговые маршруты). **Буфер сборки верфи** настоящего документа — отдельный
   **логический/инвентарный буфер** корабельного заказа (сваренный корпус + зарезервированные модули
   до финальной сборки); межпланетную логистику он **не** включает. Физическое переиспользование
   ёмкости §4.4 под сборочный буфер **не** предполагается без отдельного решения владельца — это
   разные inventory-контуры с разными инвариантами (ledger §9). Не называть логистический буфер
   §4.4 тем же складом, что и сборочный буфер заказа.

## 7. Универсальный завод комплектующих и блокировка специализациями

### 7.1 Роль и границы

- Универсальный завод комплектующих умеет производить **любой ShipModule**, включая модули профильных
  линий §6.1–6.4. Это **аварийный/стартовый путь**: позволяет построить первые корабли и добраться до
  технологий/профильных заводов.
- Это **другое производство и другой ID**, не существующий `processor` (универсальный переработчик
  руд, docs/40 §3): другой класс здания, другой набор рецептов (модули, не руды/материалы).
- Новые building records в `src/data/buildings/*` **не добавляются** этим срезом — только описываются
  (§17–18). Численные стоимость/энергия/время зданий — не выдумываются (§21).

### 7.2 Штраф 90% (интерпретация — балансное допущение) `[PROPOSED POLICY]`

- Для модулей, у которых **на этой же планете ещё не построен** профильный завод (условие блокировки —
  факт постройки, не энергосостояние, §7.3), универсальный маршрут
  разрешён со штрафом: предлагаемая интерпретация — **−90% производительности** универсального завода
  по таким рецептам, т.е. 10% обычной скорости / примерно **10× длительность** отдельного изделия.
- **Явно помечено как балансное предположение**, требующее плейтеста. Не кодировать и не менять
  остальные длительности docs/40/рецептов без источника. Альтернативная трактовка «+90% длительности»
  (~1.9×) отклонена в пользу «10% скорости» как согласующаяся со словами «штраф 90% производительности».

### 7.3 Per-planet блокировка рецептов

1. `[OWNER-DECISION]` Когда на **этой же планете** построен (**полностью завершённый**) профильный
   завод (электроники/двигателей/оружия/щитов), соответствующий рецепт универсального завода
   **блокируется для новых постановок в очередь и новых стартов**. Условие блокировки — факт
   существования законченного профильного здания, а **не** его текущее энергосостояние: выключение
   или нехватка энергии **не** открывают рецепт заново (иначе блокировка «мигала» бы при каждом
   энергодефиците и зависела бы от порядка тикания).
2. Блокировка — **локальное per-planet правило**: завод другой планеты не блокирует рецепт на текущей
   планете (общего склада/логистики между планетами нет — §5). Regression-тест на две планеты
   обязателен (§19).
3. Профильный маршрут определяется по **явному recipe/product ID** (§6.2), не по `ShipModule.category`.
4. `[PROPOSED POLICY]` Policy возврата: рецепт **снова разрешён, только когда на планете больше нет
   построенного (законченного) профильного завода** этой линии — практически, после демонтажа
   (механика сноса существует, docs/40 §9.5). Критерий — существование законченного здания, а не его
   работоспособность: обесточенный/остановленный профильный завод **не** разблокирует универсальный
   рецепт. Предположение, требующее подтверждения при runtime-дизайне (помечено явно, не решение
   владельца): достаточно ли демонтажа как единственного пути исчезновения законченного профильного
   завода, или нужен отдельный игровой выбор. Policy не зависит от случайного порядка тикания
   (детерминированная проверка состояния зданий в фиксированной фазе тика, §13).

### 7.4 Судьба уже стоящих работ при появлении профильного завода

- **Уже выполняющаяся** на универсальном заводе операция **не отменяется**: завершается без штрафной
  миграции прогресса, результат помещается в локальный буфер планеты.
- **Ещё не начатая** запись ручной очереди **сохраняется**, но помечается явным durable-статусом
  `BLOCKED_BY_SPECIALIZED_FACTORY`: не стартует и **не удаляется автоматически**; пользователь может
  отменить её вручную. Это защищает от потери заказа и упрощает save/load (round-trip статуса — §19).
- В текущей модели `ProductionItem`/`ShipyardQueueItem` durable-статуса нет (аудит D7) — для нового
  pipeline предлагается поле `status`; для legacy-записей — безопасный дефолт `QUEUED` при загрузке
  старого сейва (§18), без автоматического старта производства при deserialize.

## 8. Заказ корабля и последовательная очередь верфи

### 8.1 Фиксация состава заказа

- **ShipDesign остаётся чертяжом, а не физическим инвентарём.** Создание build order фиксирует
  выбранный дизайн/состав для конкретного заказа (снимок: hullId, armor, список `moduleIds`,
  требуемые корпусные элементы по рецепту сварки) так, чтобы **позднее изменение чертежа не меняло
  уже заказанный корабль**. В текущем runtime заказ ссылается на `designId` и дизайн читается в тик
  завершения (аудит D9) — в целевой схеме заказ хранит снимок; поле описано в §18.
- Enqueue проверяет валидность чертежа (`validateShip`, docs/50 Прил. B; уровень верфи ≥
  `requiredShipyardLevel` корпуса; требуемая технология), но **не** делает попытку «мысленно»
  засчитать детали из ручной очереди завода, уже идущих заданий, других ship project tasks или очередей
  будущих заказов. **Queue ≠ stock.**

### 8.2 Последовательность

1. Очередь заказов на верфи **последовательная**: одновременно **не более одного активного ship build
   project на одну планетарную/орбитальную верфь**. Это owner decision, superseding прежние идеи
   1–4 параллельных корабельных проектов (docs/40 §7.1 таблица, docs/50 ceil(N/2) — legacy, D2).
2. Более поздние корабли **не создают производственных задач заранее**. Их детали ставятся в
   производство **только когда заказ стал текущим на верфи** (голова очереди).
3. В момент, когда заказ становится текущим, атомарная операция (§9): читает только свободный остаток
   локального склада → резервирует подходящее количество существующих деталей → связывает reserve с
   уникальным `buildOrderId`. Свободный остаток уменьшается, reserved растёт; зарезервированное не
   видно другим заказам и не резервируется повторно.
4. Остаток требований, отсутствующий на свободном складе, формирует **только этот активный ship
   project** как недостающий demand к компонентному планировщику: на каждую недостающую позицию —
   задача производства со стабильным ID. Повторная обработка тика, повторная загрузка или повторное
   событие **не должны создавать дубликаты demand/tasks** (idempotency по стабильным ID заказа, §9/§15).

### 8.3 Сосуществование с ручными очередями (arbitration policy) `[PROPOSED POLICY]`

- Идущие вручную и уже стоящие в очередях задачи продолжают быть самостоятельными задачами; их
  **ожидаемые выходы не учитываются** как имеющиеся компоненты для нового ship order (queue ≠ stock;
  manual outputs засчитываются только после физического завершения и зачисления в stock — §19).
- Существующие ручные очереди **не перетасовываются LPT молча**. LPT применяется к независимым готовым
  задачам **ship project**; арбитраж за свободные совместимые цехи с manual jobs — явный,
  детерминированный, документированный. Рекомендуемый контракт:
  1. **активные задачи не прерывать** (доworkывают на своём цехе);
  2. **ручной FIFO-контракт сохранить** (порядок ручных команд не нарушается без решения владельца);
  3. новые ship-project задачи стартуют только на **свободных совместимых** цехах;
  4. **без starvation без явно описанного policy**: если ручной поток монопольно занимает все цехи
     линии, планировщик не встраивает ship-задачи — фиксация нехватки как наблюдаемое состояние
     (и потенциальный открытый вопрос), а не скрытое вытеснение. Финальный fair-arbitration policy —
     за владельцем (§21).

## 9. Резервирование: ledger и инварианты

### 9.1 Атомарность

- Начало корабельного заказа (активация) и резерв компонентов выполняются **атомарно** — либо reserve
  ledger и новое состояние заказа сохраняются целиком, либо не происходит ни одного изменения
  (transaction/commit ledger; в однопоточной модели — одна transакция внутри одного `commitState`).
- Резервирование/списание входов задач — атомарно и детерминированно: два завода не могут израсходовать
  один и тот же остаток (порядок обработки в тике фиксирован, §10/§13).

### 9.2 Инварианты ledger (обязательны ко всем местам резервирования)

1. `available >= 0` — всегда.
2. `reservedByBuildOrder` для детали не превышает свободный остаток, из которого она зарезервирована.
3. Одно физическое изделие имеет **ровно одно место/владение** в ledger: `free_stock`,
   `reserved_for_order`, `in_progress_output`, `assembly_buffer`, `installed_on_ship`
   (проверка conservation — §15, риск 7).
4. Завершённые изделия активного ship project **привязаны к orderId** до финальной сборки — они не
   могут одновременно попасть в свободный склад и в состав корабля.
5. Результаты (output) не теряются при переполнении: output capacity резервируется заранее или изделие
   остаётся в durable output-slot цеха (§5, §15 риск 8).
6. При отмене/ошибке загрузки — явный владелец резерва и terminal disposition для каждой детали
   (§11, §15 риск 3).

### 9.3 Reservation/refund при отмене (явное решение спецификации)

- Зарезервированные, но ещё не использованные складские компоненты освобождаются **атомарно** в фазе
  обработки команд отмены (§13) и возвращаются в `free_stock` той же планеты.
- Активные операции доworkывают; их готовые выходы возвращаются в свободный склад/буфер планеты
  (disposition `RETURN_TO_STOCK`), ровно один раз (§11).
- Готовый корпус после отмены — рекомендуемая судьба: **не scrap и не потеря**; после завершения
  активной сварки корпус/корпусная сборка попадает в отдельный учётный компонент/локальный buffer,
  пригодный к использованию следующим заказом, если корпус совместим. Если текущая модель не
  поддерживает reusable hull stock — **не вводить** численные стоимости salvage; задокументировать как
  отдельный inventory type и риск (§21).

## 10. Планировщик: детерминированный LPT

Детерминированный LPT-подобный планировщик (longest processing time first):

1. **Разложение заказа** на независимые экземпляры деталей и зависимости рецептов (**DAG**):
   узлы — задачи (сварка корпуса; по одному экземпляру на каждый элемент `moduleIds`; недостающие
   под-рецепты компонентов), рёбра — зависимости рецептов (например, плазменный двигатель требует
   двигательные секции). Циклы/неизвестные рецепты валидируются **до** создания/активации задач с
   возвратом точной причины отказа (§15, риск 9).
2. **Выбор готовых к старту задач**: только совместимые заводы (§6.2 `canProduceRecipeAtFacility`) и
   доступные материалы/энергия (per-planet, §5).
3. **Сортировка готовых задач** по убыванию ожидаемой длительности; tie-break — стабильный task ID
   (лексикографически). Назначение в совместимый свободный цех с **наименьшим ожидаемым временем
   завершения**; tie-break — facility ID, затем индекс цеха.
4. **Резервирование/списание входов** — атомарно и детерминированно (§9). Решение reservation/refund
   при отмене — зафиксировано в §9.3.
5. **Один цех — не более одного изделия одновременно**; цех не делает вещь быстрее от большего числа
   цехов. Зависимые под-рецепты соблюдают критический путь. Длительность изделия **не делится** на
   число цехов (решение владельца №6).
6. **Пример (top-throughput оценка)**: 100 одинаковых деталей / 10 заводов одинакового типа и
   длительности детали T → параллельно работают 10×W(L) цехов, волны `ceil(100/(10×W(L)))`, время
   `waves × T` (таблица в §16). В реальной смешанной системе суммарную мощность считать **только по
   заводам, совместимым с конкретным рецептом** (линии не взаимозаменяемы, §6).

**Детерминизм и инкрементальность:**

- Планировщик не запускается отдельно от детерминированного game tick и не вводит Web Workers (§4).
  Один и тот же seed/команды/тики → идентичное состояние (§19, детерминизм ≥3 процессов).
- На обычном тике продвигаются только **активные** операции: O(A), A ≤ Σ W_p. Полный граф/вся очередь
  каждый тик **не пересчитываются**; перераспределение готовых задач — по событию готовности/освобождения
  цеха (§14).

## 11. Отмена заказа и очистка очереди

### 11.1 Отмена строящегося корабля (до FINAL_ASSEMBLY)

1. Отмена **запрещает запуск любых новых работ** для этого заказа, но **не обрывает** уже работающие
   операции: они завершаются естественно.
2. Готовые модули/компоненты активных операций после отмены возвращаются в свободный склад/буфер
   **своей планеты** (disposition `RETURN_TO_STOCK`, ровно один раз).
3. Уже зарезервированные, но не использованные складские компоненты освобождаются атомарно (§9.3).
4. Активные работы, завершившиеся **после** отмены, не могут заново поставить для заказа новые работы:
   output disposition переключается на «вернуть на склад».
5. Для этого требуется durable статус заказа `CANCEL_REQUESTED`/`DRAINING` и отдельный тест
   «последний job завершился после cancel» (§19).

### 11.2 FINAL_ASSEMBLY — отмена невозможна

Как только начинается FINAL_ASSEMBLY, отмена конкретного корабля **невозможна**: API возвращает явный
результат `not cancellable` и **не мутирует состояние**. Команды clear-queue соблюдают это: не
уничтожают заказ финальной сборки и не затрагивают следующие queued orders (кроме их удаления из
очереди ожидания — см. 11.3).

### 11.3 Очистка очереди (clear queue)

- Удаляет/отменяет **будущие queued orders**.
- Активный отменяемый заказ ставит в **draining** по той же политике (11.1).
- **Не удаляет тихо** jobs, которые уже потребили ресурсы.
- Очистка во время FINAL_ASSEMBLY **не отменяет** текущий корабль, но убирает заказы, которые ещё не
  стали активными.

### 11.4 Готовый корпус при отмене `[PROPOSED POLICY]`

Не scrap и не потеря: после завершения активной сварки корпус попадает в отдельный учётный
компонент/локальный buffer, пригодный к использованию следующим заказом при совместимости
(рекомендация, **не измерено** — §20; при отсутствии в модели reusable hull stock не вводить численные
стоимости salvage, зафиксировать как отдельный inventory type и риск).

## 12. Финальная сборка и спуск на орбиту

1. На границе `READY_FOR_ASSEMBLY → FINAL_ASSEMBLY` **валидатор подтверждает**: корпус и каждая
   требуемая деталь присутствуют в локальном assembly buffer, зарезервированы за этим `buildOrderId`,
   и ни одна не уже использована.
2. **Одним commit** детали потребляются из reserve/buffer и создаётся корабль: ровно один новый `Ship`,
   одна запись сборки, одно списание каждой физической детали.
3. События/повторные тики **idempotent**: ровно один новый Ship, одна запись сборки, одно списание —
   на стабильных ID задач/выходов и проверяемом состоянии заказа, не надеясь на отсутствие повторного
   вызова (§15, риск 2).
4. Корабль появляется на орбите планеты верфи (`location = planet.id`, owner — как в текущем
   `processShipyardTick`); расчёт HP/состава — из зафиксированного снимка дизайна заказа (§8.1).
5. При reload reserve ledger, cancelled/draining jobs, completed modules и assembly boundary
   **round-trip без duplication/loss** (§19).

## 13. Фиксированный порядок фаз тика

Порядок фаз **фиксирован** (снимает гонку «cancel в тот же тик, когда scheduler создаёт новый job»):

```
1. Обработать команды отмены/очистки (cancel/clear)
2. Запретить создание новых работ для draining заказов
3. Продвинуть уже активные работы (O(A))
4. Однократно маршрутизировать завершённые output в склад/буфер
5. Проверить переход активного неотменённого заказа к FINAL_ASSEMBLY
```

Дополнения к контракту тика (существующий runtime сохраняется):

- Симуляция однопоточная; всё планирование — внутри детерминированного game tick, один авторитетный
  `commitState` (Pattern A). Web Workers не вводятся (§4, §10).
- Policy блокировки/разблокировки универсальных рецептов (§7.3 п.4) вычисляется в фиксированной фазе
  (шаг 2/3), не завися от случайного порядка подписчиков.
- ShipsModule продолжает обрабатывать legacy `shipyardQueues` как сегодня (SHIPFLOW-00: коммит при
  любом изменении очереди); новый pipeline в runtime-срезе подключается отдельным модулем/фазой —
  не дублируя текущий движок (§17).

## 14. Производительность и предварительный риск-анализ

Это оценка сложности, **не benchmark**: реальные тайминги/число планет/цехов в целевой игре ещё не
измерены. Обозначения: P = число активных планет; W_p = число реально занятых цехов на планете p;
A = сумма активных задач; J = число ожидающих/готовых задач одного активного проекта; M = число
требуемых позиций модулей; E = число recipe dependency edges.

| Операция | Стоимость | Комментарий |
|---|---|---|
| Создание проекта и графа зависимостей | O(M + E) | выявление циклов/неизвестных рецептов — тоже O(M+E), **один раз** при активации заказа |
| Обычный тик | O(A), A ≤ Σ W_p | продвигать только активные операции; **не** пересчитывать весь граф/всю очередь заново каждый tick |
| Планирование на событии готовности/освобождения цеха | полная сортировка O(J log J); рекомендовано deterministic ready-heap/ordered queue → enqueue/dequeue O(log J) | событие, не каждый тик |
| Проверка ресурсов | O(k), k = число ингредиентов конкретного рецепта | **не** сканирование всего мира/инвентаря |

- Иллюстративная нагрузка: 10 планет × 10 заводов-компонентников/планету × 10 цехов/завод = порядка
  **1 000** активных workshop slots; 100 таких планет — порядка **10 000** slots. Это не утверждение о
  FPS/мс — только счёт активных сущностей на тик. Нужны bench/profiling на реальном симуляционном
  наборе до выбора точных границ.
- Вероятные CPU bottleneck'и (профилировать в первую очередь): полная повторная сортировка всех задач
  каждый тик; полные обходы/копирование всей GameState; множество React/UI-обновлений для каждого цеха
  (UI state батчить); пересчёт recipe graph; перебор склада по всем building instances.
- Сначала простой детерминированный engine, затем измерение и оптимизация по профилю.
- UI-обновления батчить; подписки — на события заказа/задачи, не на каждый цех отдельно (§15, риск 12).

## 15. Failure analysis: что может сломаться и требуемая защита

| # | Что может сломаться | Требуемая защита |
|---|---|---|
| 1 | Двойное резервирование одной детали двумя заказами/верфями | transaction/commit ledger, стабильный order ID, атомарный subtract+reserve, invariant-тесты |
| 2 | Дублирование завершённого модуля/корабля из повторного tick/event/save-load | однократный переход job/order статуса, стабильный output ID, idempotency-тесты |
| 3 | Утечка резервов при отмене/ошибке загрузки | явный владелец (owner) каждого резерва и terminal disposition для каждой детали |
| 4 | Рецепт доступен через один обход API (UI разрешает, backend запрещает — или наоборот) | централизованный `canProduceRecipeAtFacility(...)`; UI/backend/start-scheduler тестируются **одним** набором таблиц |
| 5 | Ручная очередь пропала/зависла после появления специализации | preserve blocked entry (`BLOCKED_BY_SPECIALIZED_FACTORY`), статусы, cancellation API, round-trip тесты |
| 6 | Cancel race: расписание создаёт новые jobs после отмены | фиксированный порядок command/tick фаз (§13) и draining state |
| 7 | Компонент «и на складе, и в reserve» либо потерян между factory/output/assembly buffer | единая ledger transition, проверка conservation (§9.2) |
| 8 | Склад переполнен при завершении задачи | заранее резервировать output capacity или хранить завершённый output в durable output-slot цеха; **нельзя** молча выбрасывать изделие/повторять completion |
| 9 | Неизвестный рецепт/цикл зависимостей навсегда блокирует заказ | валидировать DAG **до** создания/активации задач, возвращать точную причину отказа |
| 10 | Ручное производство starve'ит ship project либо LPT молча переупорядочивает manual queue | отдельная fair arbitration policy (§8.3); не нарушать активные job и FIFO ручных команд без решения владельца |
| 11 | Legacy save теряет очередь или создаёт новые job при загрузке | миграция, воспроизводимая из legacy state; никакого нового производства автоматически при deserialize — только явный tick/command |
| 12 | Нагрузка UI/симуляции растёт как O(all jobs log all jobs) per tick | активные jobs O(A); ready scheduler event-driven/heap; UI state батчить; подтвердить profiling |
| 13 | Специализированный завод блокирует рецепт не на той планете | facility lookup строго scoped to planet ID; regression-тесты на две планеты |
| 14 | Рецепты документа §6 не совпадают с каталогом ShipModule | versioned explicit mapping/table + validator (§6.3); никакого маршрута только по category name |

## 16. Баланс цехов W(L) — таблицы до уровня 10

Число цехов производственного завода уровня L — W(L). Сравнения при W(1)=1.

**Модели:**

- **Линейная (рекомендуемая), W(3)=3:** `W(L) = L`.
- **Линейная с бонусом, W(3)=4:** целочисленная модель с бонусным цехом на L3, затем +1 за уровень:
  1, 2, 4, 5, 6, 7, 8, 9, 10, 11. **Явное пояснение:** «1, 2, 4» — **не** строгая целочисленная
  арифметическая прогрессия с одинаковым шагом; строгая прогрессия с W(1)=1 и W(3)=4 невозможна при
  целочисленном одинаковом шаге. Для сравнения зафиксирован отдельный бонусный цех на L3, затем +1/уровень.
- **Квадратичная альтернатива, W(3)=3:** `W(L) = round(1 + 2 × ((L−1)/2)²)`.
- **Квадратичная альтернатива, W(3)=4:** `W(L) = round(1 + 3 × ((L−1)/2)²)`.

**Округление:** единое правило для обеих квадратичных моделей — nearest integer, half-up.

### 16.2 Throughput-пример: 100 одинаковых деталей / 10 совместимых заводов

Каждый цех обслуживает одну деталь за T. «Волн» = `ceil(100/(10 × W(L)))`; суммарно одновременно
работающих цехов = 10 × W(L); ideal elapsed time = waves × T. Это **только throughput-верхняя оценка**:
без resource bottleneck, зависимостей и транспорта.

> считать только по совместимым заводам конкретного рецепта (§10 п.6).

### 16.3 Правило двойного масштабирования (запрет)

**Не применять W(L) как дополнительный speed multiplier**: число цехов определяет **параллельную
вместимость**; скорость отдельного цеха берётся из рецепта и разрешённых модификаторов (adjacency
bonus, workforce efficiency — по действующим правилам docs/40). Иначе апгрейд завода дважды раздует
производительность (W(L) растёт × скорость).

### 16.4 Рекомендация `[PROPOSED POLICY — ожидает финального закрепления владельцем]`

**Рекомендуемый вариант — арифметический линейный `W(L)=L`** (3 цеха на L3; соответствует выраженному
владельцем предпочтению, §1 п.7 — «предпочтение» трактуется как рекомендация базовой модели, а не
как окончательно зафиксированное решение):

- прост для игрока и для UI (заводы уровней 1..10 дают 1..10 цехов);
- без квадратичного взрыва на уровнях 4–10 (квадратичные модели дают 42–62 цеха на одно здание
  против 10–11 у линейных — наглядный аргумент);
- совместим с фиксированным порядком тикания и O(A)-границами (§14).

**Вариант «4 цеха на L3»** — только как осознанный milestone-бонус, если владелец примет нелинейный
скачок на переходе L2→L3 (не строгая арифметическая прогрессия — см. §16 пояснение).

**Строительная цена/энергия новых заводов не выдумываются** — см. список необходимых решений/данных (§21).

## 17. Расширение текущей системы рецептов/очередей (не дублирующий движок)

Целевая реализация **переиспользует** действующие механизмы, а не создаёт параллельный движок:

1. **Рецепты** — `RecipeDef` (`src/data/recipes.ts`) остаётся основой. Предлагаемые опциональные
   поля-расширения (все — предложения, не runtime):
   - `productKind?: 'component' | 'shipModule' | 'hullElement'` — класс изделия;
   - `moduleId?: string` — явная связь выхода рецепта с ID каталога ShipModule (устраняет разрыв
     `ion_engine` vs `engine_ion_mk1`, аудит D5);
   - `facilityLine?: 'electronics' | 'engine' | 'weapon' | 'shield' | 'hull' | 'universal_component'` —
     явная принадлежность линии (маршрутизация по ID, не по category);
   - `universalAllowed?: boolean` — признак «может производить универсальный завод» (для компонентов
     §6.5, корпусных элементов и модулей).
2. **Очереди**: планетарное производство — эволюция `ProductionQueue`/`ProductionItem` (карусель R-26
   сохраняется как механизм назначения на экземпляры зданий); ship build orders — эволюция
   `ShipyardQueue` (последовательная FIFO — уже соответствует утверждённому правилу одного активного
   проекта). Дублирующий parallel engine не вводится.
3. **Модульные задачи** ship project'а — новый тип записи (§18) со стабильным ID
   `orderId + index + moduleId`, планирование LPT (§10) только для них; арбитраж с ручными задачами —
   §8.3.
4. **Категории рецептов** `RecipeCategory` (`raw_to_material/material_to_component/component_to_module/
   module_to_ship`) сохраняются; legacy-семантика `component_to_module` на верфи перенастраивается на
   планетарные заводы (D3) — отдельным шагом миграции, не в этом срезе.
5. **Пробелы данных** (зафиксированы, не заполняются числами):
   - у ShipModule нет `productionTime`/`recipeId` (аудит D11);
   - у большинства ShipModule нет производственных рецептов вовсе (§6.3/Б);
   - нет рецептов для корпусных элементов трёх размеров §6.5 (в каталоге один `hull_element`);
   - нет рецепта сварки корпуса из корпусных элементов (операция HULL_WELDING — новая).
   Предложение: добавить опциональные поля (`ShipModule.productionRecipeId?`, `ShipModule.productionTime?`,
   рецепт сварки корпуса `weld_hull_<size>` с входом из корпусных элементов §6.5) — **числа задаёт
   владелец отдельным решением**.

## 18. Данные и сейв: будущие поля и обратная совместимость

Новые building records и поля сейва в этом срезе **только описываются** (runtime не меняется):

1. **Новые building records (будущее):** `electronics_plant`, `engine_plant`, `weapon_plant`,
   `shield_plant`, `hull_plant` (docs/40 §6.1–6.5), `universal_component_factory` (новый ID, §7).
   В `src/data/buildings/surface.json` их сейчас нет (аудит D4) — добавление = отдельный runtime-срез.
2. **Будущий pipeline-контур (предложение структур, optional-поля):**
   - `PlanetProductionPipeline` per planet: component buffer, reserve ledger, assembly buffer(s) верфи;
   - `ShipBuildOrder`: `id (buildOrderId)`, `shipyardRef`, `designSnapshot` (снимок состава, §8.1),
     `status` (§4), `moduleJobs[]` (стабильные ID, статусы), `hullWelding` (операция), `createdAtTick`;
   - `ModuleJob`: `id = orderId + index + moduleId`, `status` (`QUEUED/RUNNING/COMPLETED/
     BLOCKED_BY_SPECIALIZED_FACTORY`), `facilityRef`, `progressTicks/totalTicks`.
3. **Обратная совместимость (обязательные контракты):**
   - старые сейвы **без** новых полей продолжают загружаться: pipeline-поля опциональны, при
     deserialize — безопасный default «production pipeline пуст»;
   - **legacy-заказы** в старой `ShipyardQueue` не теряются и не пересчитываются задним числом
     (без скрытого repricing и без сброса прогресса);
   - никакого нового производства автоматически при deserialize — только явный tick/command (§15, риск 11);
   - миграция, воспроизводимая из legacy state (тест §19).
4. **Честный путь миграции legacy-очереди верфи (уточнено DOC-AUDIT-01).** Старый `ShipyardQueueItem`
   (`{ designId, shipName, progressTicks, totalTicks }`) **не содержит** снимка состава дизайна
   (`designSnapshot`): если чертёж редактировался после постановки в очередь, исторический состав
   заказа **восстановить нельзя** — и спецификация не делает вид, что он известен:
   - рекомендуемый путь: legacy-заказы дорабатываются **существующим legacy-контуром** (целочисленный
     прогресс всего корабля, списание в тик завершения — как после SHIPFLOW-00), без переноса в новый
     pipeline, без пересчёта стоимости/длительности/прогресса и без реконструкции снимка;
   - **новые** build orders создаются **только** по новому контракту (снимок состава фиксируется в
     момент enqueue, §8.1);
   - `status` = `QUEUED` (дефолт) применяется **только к записям нового формата**; legacy-записи
     остаются в прежней форме и валидны без поля статуса;
   - альтернатива «реконструировать снимок при миграции из текущего состояния дизайна» отклонена
     как нечестная: дизайн мог измениться после постановки в очередь (аудит D9).
5. **Сериализация**: новые Map'ы — entries-массивами (как текущие `productionQueues`/`shipyardQueues`
   в `game-store.ts`); строгая валидация при загрузке (zod-схема по образцу save v3): неизвестные
   версии/битые секции — явный отказ, не тихий дефолт.

## 19. Тестовые контракты для будущего runtime-среза

Документируются **сейчас**, реализуются в отдельном runtime-срезе (не в SHIPFLOW-DOCS):

1. Две планеты одновременно: склад, буфер и резерв полностью изолированы; деталь нельзя заказать с
   планеты A из склада B.
2. Две верфи/два заказа, конкурирующие за последнюю одну деталь: ровно один reserve успешен,
   `available` не уходит ниже нуля.
3. При enqueue заказ не создаёт module jobs и не резервирует inventory; когда заказ достигает головы
   очереди, snapshot склада атомарно резервируется, missing counts создают **ровно один** набор jobs.
4. Manual queued/active outputs не засчитываются как stock, пока физически не завершены и не зачислены
   в stock.
5. Universal plant: может делать модуль при отсутствии local specialty; штраф действует только на
   processing duration/rate; после появления specialty нельзя enqueue/start universal job для этой
   линейки; active universal task finishes; not-started manual item gets blocked, not deleted.
6. Cancel ship before final assembly: active jobs finish, no follow-on tasks, reserved stock released,
   finished outputs/finished hull return to local stock/buffer **exactly once**; cancel at/after assembly
   returns explicit refusal and changes nothing.
7. Clear queue cancels waiting orders, drains active cancellable order, respects active final assembly.
8. Save/load в каждой фазе жизненного цикла: queued, reserve transaction, jobs running, draining after
   cancel, ready for assembly, final assembly. No duplicate outputs, no reservation leak.
9. Full storage at output completion cannot lose the output.
10. Determinism across ≥3 independent processes for same seed/commands/ticks.
11. Single active ship project per shipyard; no jobs spawned for later orders.
12. Baseline-гейты при реализации: текущие 906+ тестов (после SHIPFLOW-00 — 906/906), lint (0 errors /
    38 warnings), tsc exact exit/baseline (исторический ненулевой exit **не** именовать PASS), validate:all;
    CI не заявлять без реально наблюдаемых workflows/check-runs.

## 20. Продуктовые допущения (не хардкодить молча)

Следующие трактовки — **допущения**, явно выставленные в документации и ожидающие плейтеста/решения;
в runtime их не «зашивать» незаметно:

1. «Штраф 90%» трактуется как **−90% скорости** (10× длительность), а не +90% длительности.
2. Universal recipe lock действует **per planet** при наличии **построенного (законченного)**
   профильного завода на этой планете; энергосостояние завода (обесточен/выключен) блокировку
   **не** снимает (§7.3).
3. Running universal jobs **finish**; not-started queued jobs остаются **blocked**, не удаляются.
4. Рекомендовано, но **не измерено**: текущая сварка корпуса завершается после отмены, готовый корпус
   попадает в reusable local hull buffer.
5. Требуется финальный policy по output capacity заводов и арбитражу manual FIFO vs ship-project LPT.
6. Нет межпланетной логистики, нет cross-planet inventory, нет новых численных стоимостей/времён без
   явного решения владельца.
