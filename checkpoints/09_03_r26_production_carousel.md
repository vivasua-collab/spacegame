### Баг 3 — параллельная карусель производства (engine.ts)
- Прежде: processProductionQueue обрабатывал ТОЛЬКО queue.items[0] → второй
  автоповтор не двигался никогда.
- Теперь: одновременно работает столько задач, сколько экземпляров здания
  (recipe.buildingId) на планете. Назначение задач на экземпляры:
  1. липкое назначение (assignedTo) — задача в процессе остаётся на своём экземпляре;
  2. карусель FIFO: 2 переработчика + 3 задачи → работают 2, третья ждёт слот;
  3. автоповтор занимает слот постоянно — два автоповтора при двух переработчиках
     работают одновременно.
- Энергия списывается для каждой активной задачи отдельно (P3-02 сохранён).
- ProductionItem.assignedTo — ключ экземпляра (hexIndex / -1-i / -100-i), UI
  показывает бейдж исполнителя («→ гекс #N»).

### Баг 4 — приоритет специализации (два варианта, выбран №1)
- **Вариант 1 (выбран):** приоритет в ОБЩЕЙ карусели — специализированный
  переработчик первым берёт задачи своей категории (вне позиции в очереди),
  правило карусели для него отменяется; берёт ТОЛЬКО свою категорию (нет задач —
  простаивает, игрок может откатить специализацию).
  - Меньше багов: без смены схемы сейва, без нового UI, назначение
    детерминировано, вся логика в одном месте (assignQueueTasks).
- **Вариант 2 (отклонён):** отдельная карусель в каждом специализированном
  переработчике — требует per-building очередей (смена схемы сейва, миграции,
  новый UI, дублирование логики) → высокий риск регрессий.
- Попутно найден корень «переработчики не работают»: приоритет никогда не
  применялся, т.к. recipe.processorCategory передавался, но findProcessorInstance
  брал «первый попавшийся» экземпляр; кроме того у построенных refinery/synthesizer
  processorType не инициализировался (дефолты из BuildingDef теперь ставятся
  в buildOn* + resolveType в collectProcessorInstances).
- Реальная причина простоя переработчиков у игрока: отрицательный энергобаланс
  (P3-02 блокирует задачи при нехватке энергии) — подтверждено в браузере:
  после постройки ядерного реактора обе задачи пошли.

### Ленивая генерация — ДИЗАЙН (на согласование, не реализовано)
1. При генерации галактики: для каждой планеты считается верхнеуровневый пул
   `resourcePool: { elementId → total }` (сумма того, что дали бы гексы).
   Порядок вызовов PRNG сохраняется (детерминизм), детали гексов НЕ пишутся в state.
2. При колонизации планеты: гексы генерируются на лету из подпотока PRNG
   (seed = galaxySeed ⊕ planetId) → распределение залежей восстанавливается
   детерминированно; пул = контрольная сумма.
3. В сейв попадают только гексы колонизированных планет: старт ~5.5 MB вместо
   36.8 MB, размер растёт с колонизацией; истощённые гексы (0 ресурсов)
   на поздних стадиях — естественная экономия.
4. Мобильные добытчики: «садятся сами» — планетарная карусель добычи (аналог
   карусели производства), без ручного «сажания» на каждый гекс.
5. Риски: PRNG-детерминизм (как в аудите JSON-extraction), galaxy-snapshot
   тесты потребуют обновления, UI гекс-грида неколонизированных планет →
   заглушка «не разведана» + пул. Оценка: ~2-3 сессии работы.
