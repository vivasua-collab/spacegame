- `dmesg`: **два kernel OOM-kill за день**:
  1. uptime 24135s — убит `bun` (anon-rss 1.74 ГБ) — мой первый полный `bun test`;
  2. uptime 31251s — `bun invoked oom-killer` → ядро выбрало **`next-server` (anon-rss

- Turbopack-девсервер держит **1.7–1.8 ГБ RSS постоянно** — крупнейший процесс системы
  (4 ГБ RAM, swap нет) → при любом тяжёлом соседе (полные гейты, Chromium, генерация
  галактики) ядро убивает крупнейшего.
- Сигнатура владельческого инцидента #18 совпадает: в dev-логе окна плейтеста НЕТ ни
  одного POST/PUT (запрос не дошёл/сервер был в шторме), и окно совпало с тяжёлыми

## 4. Доказанный кодовый дефект + фикс: ambiguous POST → дубль (§6)

**Воспроизведение** (raw TCP, §6): валидный POST, соединение закрыто ДО чтения ответа →
сервер завершил запрос (201, INSERT), **строка осталась в БД** → клиент не получил {id},
currentSaveId не установлен → повторный Save = второй POST = **дубль «Galaxy #seed»**.

**Фикс (узкий, схема БД и v4 не тронуты):**
- `src/lib/save-request-dedup.ts` (новый): Map requestId→saveId, TTL 10 мин, cap 500
  (eviction старейшего), `isPlausibleSaveRequestId` (8–64, [A-Za-z0-9_-]), тест-only reset.
- POST `/api/save`: requestId из header `x-save-request-id` (кривой → игнор); старт-лог с
  `requestId=`; дедуп-проверка ПОСЛЕ zod и ДО decode; хит → `200 {id, deduplicated:true}`
  БЕЗ новой записи; после create → `rememberSaveRequest`.
- PUT `/api/save/[id]`: requestId в старт-лог (корреляция §4); дедуп не нужен (идемпотентен
  по ID записи естественно).
- Клиент `game-store.ts saveGame`: `acquireSaveRequestId(sessionVersion)` ДО fetch; header на
  POST и PUT; **ID переживает неудачную попытку** (retry той же операции), **освобождается
  успехом**; привязка к монотонному `sessionVersion` (newGame/успешный loadGame/restore)
  не даёт ID утечь в чужую игру; requestId в `[save] OK` и в `Save failed`-диагностике.
- Ограничение гарантии (честно): in-memory одного процесса — рестарт сервера между
  попыткой и повтором сужает гарантию (редкое окно, принято осознанно).

**End-to-end доказательство на реальном сервере** (2026-10-31):
- TCP-пробой с `x-save-request-id=proof-dedup-e2e-20261031-ok` → запись `DEDUP-PROOF-STEP1` создана;
- curl-повтор с тем же requestId и ДРУГИМ payload → `HTTP 200 {"id":"cmvwmjhtc…","deduplicated":true}`;
- в БД ровно **1** запись; серверный лог: start(96B, requestId=…) → start(95B) → dedup-hit
  `-> existing save cmvwmjhtc… (новая запись НЕ создаётся)`.

## 7. Остаточные риски / открытые вопросы (за владельцем)

1. Среда 4 ГБ/без swap: рекомендация владельцу — не совмещать тяжёлые гейты агента с
   плейтестом; при повторе инцидента прислать `Save failed: {...}` detail из консоли —
   теперь он содержит requestId, по которому серверный лог однозначно отвечает «дошёл ли
   запрос и был ли commit» (§4 корреляция готова).
2. Внешний preview-прокси платформы недиагностируем изнутри песочницы (нет hostname);
   если инцидент повторится при спокойной среде — следующая точка трассировки там.
3. Дедуп — in-memory одного процесса (рестарт между попыткой и повтором сужает гарантию);
   при желании владелец может запросить персистентность ключей (схема БД + миграция) —
   сознательно НЕ сделано без доказанной необходимости (§6).
4. SAVE_REQUEST_TIMEOUT_MS = 30 с намеренно НЕ увеличен (§7 запрет); запас измеренный — ≥24×.
