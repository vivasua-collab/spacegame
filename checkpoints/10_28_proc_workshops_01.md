## Что сделано

Цеховая модель переработки (docs/40-buildings.md v3.0, решения владельца 2026-10-28):

- **Уровень processing-здания = количество цехов** (1→1, 5→5, 10→10); один цех — одна партия одновременно; уровневый множитель скорости переработки отменён (пропускная способность = число цехов); синергия соседства сохранена.
- **Специализация на цехе по конкретному recipeId** (каталог `workshop-specializations.ts`: ID/имя/совместимый пул), с уровня здания 1, уровни 1–5 прежней формулой стоимости; **необратима** (снять/сменить/понизить нельзя; «Вернуть к универсальному» удалён).
- **Детерминированный планировщик** (`workshop-scheduler.ts`): специалист-приоритет (player-FIFO → профильный авто-кандидат) → общий FIFO (специалисты без профильной задачи работают как обычные, БЕЗ второго штрафа — ×0.75 baseYield) → авто-кандидаты R-27 (Fe→Si→Al→C→Cu→Ti, входы над резервным полем). Runnable-гейты: входы/энергия per-tick/место под все выходы (canStoreResource) — недоступная задача не занимает цех и не блокирует доступные. Начатая партия не прерывается; repeat → хвост пула; одна задача ≠ два цеха.
- **Два изолированных пула**: `processor` (продвинутые/прочие рецепты) + НОВОЕ здание `construction_materials_plant` (поверхность, L1–10) для 6 базовых рецептов R-27 (smelt_fe/si/al/c/cu/ti + руды Fe/Si/Al/C/Cu/Ti-ore перенесены в строительный пул). Задача одного пула никогда не занимает цех другого.
- **R-27 авто-режим через планировщик**: `processAutoProcessing` (обходной цикл вне ограничения рабочих мест) УДАЛЁН как вторая исполнительная дорога; авто-партии — обычные партии цехов (`WorkshopBatch.queueItemId: null`), ограничены конечной вместимостью; несколько заказов одного рецепта — отдельные входные ресурсы.
- **Понижение L→L−1 удаляет цех №L**: занятый — партия в хвост FIFO с сохранённым прогрессом (заказ не пересоздаётся); специализированный — вложения теряются безвозвратно; upgrade → новый plain-цех; снос — все цехи по тем же правилам.
- **Сейвы**: старые сейвы НЕ требование совместимости (п.12 issue) — при загрузке защитная нормализация (обычные цехи по buildingLevel; категорийные специализации processor НЕ мигрируются — задокументированная несовместимость); save v3 — компактная сериализация workshops (spec/level/batch); битые партии с несуществующими queueItemId снимаются.
- **UI**: панель цехов 1..L (статус/профиль/уровень/партия/прогресс/причина ожидания), диалог специализации по рецептам пула с обязательным предупреждением необратимости, «Улучшить специализацию» с ценой ×level, апгрейд-подсказка «+1 обычный цех», понижение «−цех №L» с предупреждением потери, исполнитель-бейдж «гекс #N · цех M» (lookup, не сохраняемая привязка — `assignedTo` удалён), очереди производства: раздельные секции пулов + статусы задач (выполняется/в очереди/пропущена: причина).
- **Не тронуто**: корабельные компоненты, верфи, docs/55-ship-production-flow.md; refinery/synthesizer — прежняя категорийная карусель (display-only панель).

## Известные ограничения

- Старые сейвы: категорийные специализации processor не переносятся (явное решение issue п.12); при загрузке — обычные цехи.
- Энергия авто-партий: recipe.energyCost/total за тик (раньше авто-режим R-27 энергию рецепта не тратил — изменение задокументировано в §11.4).
- **P1 — не принято, выявлено статическим аудитом 2026-10-29:** если входы исчезли к моменту завершения партии (например, параллельный заказ забрал общий остаток), player-партия сбрасывает remaining progress в `0` и продолжает удерживать цех. Это может навсегда блокировать следующий заказ и противоречит требованию Issue #23, что заблокированная задача не starvation-ит доступные. Исправить и покрыть регрессионным тестом; см. комментарий аудита в [Issue #23](https://github.com/vivasua-collab/spacegame/issues/23).

## Аудиторское дополнение — 2026-10-29

Статическая проверка текущего runtime на [коммите `7d752fa`](https://github.com/vivasua-collab/spacegame/commit/7d752fa1e0a25db20a7fef9a191c227ca1f81cc9) обнаружила два критерия, которые пока нельзя считать принятыми:

1. **P1 — конкурентный старт переоценивает доступные входы.** `runWorkshopPoolTick` отдельно проверяет каждый заказ через `getRecipeRunability` до назначения всех свободных цехов. Два заказа `smelt_fe` могут одновременно пройти гейт при `Fe-ore = 10` (сырья на одну партию). Первая партия спишет руду; вторая достигнет `progress = 0`, останется в `currentBatch` и будет продолжать занимать цех. UI при этом сначала находит исполнителя и показывает задачу как выполняющуюся, а не пропущенную из-за входов. Текущий C7-тест проверяет только отсутствие сырья *до начала* задачи и не ловит этот сценарий.

2. **P1 — нет общей резервации места на выходы конкурирующих партий.** Каждый заказ индивидуально проверяет склад на момент планирования; завершение напрямую прибавляет `produced` к ресурсам без повторной проверки ёмкости. Два цеха могут стартовать партии, каждая из которых помещается в текущий остаток склада отдельно, но вместе они могут его переполнить. Гейт также проверяет номинальный выход рецепта без бонусного `yieldMult` специализированного цеха. Нужны безопасное резервирование или повторная проверка/перепланирование и регрессионные тесты.

**Объём аудита:** это статический просмотр GitHub-кода и тестов. В рамках данного аудита независимый запуск `bun test`, браузерного E2E и ручной игры не выполнялся. Числа командных прогонов выше — задокументированный отчёт кодера, не независимый результат аудитора. Issue оставлена открытой до устранения finding'ов и ручного плейтеста владельца.
