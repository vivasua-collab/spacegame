## §2. Исправления (минимальные, локальные)

### F-01 `src/core/typed-event-bus.ts`
- Replay-доставка для `once`-подписки считается первым (и единственным) вызовом: подписка снимается НЕМЕДЛЕННО в `finally` после доставки.

### F-02 `src/core/game-loop.ts`
- `setSpeed(0)` при playing теперь вызывает тот же явный путь паузы: фаза `paused` + **`core:paused`** + остановка интервала. Контракт унифицирован: `setSpeed(0)` ≡ `pause()` (плюс `core:speed-changed`).
- `start()` различает первый запуск (`core:started`) и возобновление (`core:resumed` — событие было объявлено в `events.ts`/`modular-bus.md`, но не эмитилось никем; тот же класс дефекта, что `tech:fundamental-leveled` до R-39).
- `stop()` документирован как TEARDOWN-путь (React unmount, `mediator.stop()`): фаза → `paused`, интервал остановлен, БЕЗ `core:paused` (сознательный контракт, зафиксирован тестом; прежний комментарий «без изменения фазы» противоречил коду). Обоснование: фаза ДОЛЖНА уходить из `playing`, иначе повторный `start()` после remount был бы no-op.
- Семантика ×1/×5/×15/×50, догоняющие тики (catch-up с переякориванием при катастрофическом отставании — без лавины тиков), загрузка времени из сейва (`setTime` + `step` — время не применяется дважды), граница года 364→365 (`core:year` ровно один раз) — покрыты тестами, регрессий не внесено.

### F-03 `src/core/module-registry.ts`
- Регистрация АТОМАРНА: порядок сначала вычисляется на «пробной» установке; при ошибке (цикл) Map откатывается к прежнему значению — новый модуль удалён / заменённый возвращён, старый модуль НЕ уничтожен, `initOrder` не менялся (присваивается только после успешного обхода).
- Заменённый модуль уничтожается ТОЛЬКО после успешного пересчёта порядка.
- Восстановление после исключения без пересоздания игры: тест подтверждает, что после отката можно зарегистрировать корректный модуль и работать.

### Попутные усиления шины (найдены при аудите, вне трёх находок)
- `flush()`: защитный лимит `MAX_FLUSH_BATCHES = 1000` — обработчик, безусловно повторно defer-ящий событие, прежде зацикливал flush навсегда (подтверждено зависанием теста). Повторный defer внутри flush по-прежнему обрабатывается следующим пакетом того же flush.

## §10. Follow-up (2026-10-27, план владельца в комментарии к Issue #6): контракт once при вложенном emit

### §10.1 Признание пробела первоначального R-42

Первоначальный F-01-фикс R-42 устранил двойной вызов для пары «replay + следующий
emit», но оставил незакрытым контракт `once` при ВЛОЖЕННОМ синхронном emit того же
события. Три сценария двойного вызова на опубликованном R-42:

| # | Сценарий | Причина на дефектном коде |
|---|----------|---------------------------|
| a | Вложенный emit того же события из replay-обработчика | Подписка снималась в `finally` ПОСЛЕ вызова обработчика — вложенный dispatch находил её в Set |
| b | Вложенный emit из самого once-обработчика | `emit()` откладывал удаление в `toRemove` до конца обхода snapshot — вложенный snapshot содержал подписку |
| c | Вложенный emit из обычного обработчика с более высоким приоритетом ДО достижения once во внешнем обходе | Вложенный dispatch вызывал и удалял once-подписку, но внешний snapshot всё ещё содержал её — второй вызов при продолжении внешнего цикла |

### §10.3 Фикс (только `src/core/typed-event-bus.ts`, по рекомендованной стратегии владельца)

- В `Subscription` добавлен явный признак потребления `consumed: boolean` (инициализация при создании).
- **Replay-путь `on()`:** once-подписка помечается потреблённой и удаляется из Set **ДО** вызова обработчика (прежде — `finally` после). Ошибка обработчика потребление не отменяет (подписка не восстанавливается).
- **`emit()`:** перед вызовом once-подписки она помечается потреблённой и удаляется из Set; элемент устаревшего внешнего snapshot пропускается по флагу `consumed` — **только для once**. Проверка принадлежности Set для ОБЫЧНЫХ подписок не вводилась: snapshot-семантика «подписка, отписанная во время dispatch, ещё вызывается в текущем dispatch» сохранена (существующий тест R-42 остался зелёным).
- Механизм `toRemove` удалён за ненадобностью (упростил код; связанного рефакторинга нет).
- Без изменений: изоляция исключений (`emit`/replay-путь), стабильная сортировка по priority и порядок при равных, вложенный синхронный emit, replay для не-once подписок, функция отписки, `defer/flush` (включая MAX_FLUSH_BATCHES), `clear()`.
- GameLoop и ModuleRegistry не тронуты (их фиксы — в опубликованном R-42); экономика, PRNG, формат сейва, API не затронуты.
