# Task 29 (R-29): ленивая материализация залежей + fmt v3

Дата: 2026-08-31. Владелец: «Теории генерации. Как идея, не выполнять полное
запекания гексов планет: у планеты есть верхнеуровневый пул ресурсов каждого
рудного элемента (общее число); ресурсы на гексах генерируются только при
колонизации. Мобильным добытчикам не нужно "сажать" на каждый гекс — садится
сам. В сейв не попадают мёртвые (не разведанные) гексы — файл на начальном
этапе меньше; на поздних этапах часть гексов истощена (по 0) — тоже проще.»

Плюс два сопутствующих запроса: где физически хранятся сейвы; актуализировать
INSTRUCTIONS.md (крах DEV-сервера).

## 1. Анализ идеи

Идея владельца совпадает с паттерном lazy materialization:

| Аспект | Было (R-28) | Стало (R-29) |
|---|---|---|
| Генерация | `assignResourceDeposits` запекает залежи во ВСЕ гексы всех 949 тел (531 планета + 418 лун) | «Прогон» той же функции на реальной сетке → агрегат-пул сохраняется, залежи СТИРАЮТСЯ; сохраняется RNG-состояние `depositRngState` (снимок ДО прогона) |
| Пул | свод `resourceDeposits` (вычислялся из запечённых гексов) | тот же свод — теперь ОН источник истины «сколько всего» (то, что владелец называет «верхнеуровневый пул») |
| Материализация | — | `colonizePlanet()` → `materializePlanetDeposits(planet)`: replay `assignResourceDeposits` из сохранённого RNG-состояния → бит-в-бит те же залежи, что дал бы прогон при генерации |
| Мобильные добытчики | будущие корабли-добытчики требовали бы запечённых залежей на каждом гексе | любая единица «садится сама»: гексы планеты материализуются при колонизации — посадка на любой гекс валидна (буд. фича docs/35 §4.3) |
| Сейв | все 276k залежей всех тел | только материализованные тела; пула хватает для скана |
| Истощение | кортежи с qty=0 хранятся вечно | v3 НЕ пишет кортежи с qty<=0 («истощённые гексы проще»); флаг `dm` предотвращает повторную материализацию |

Ключевой трюк воспроизводимости: `Xoshiro256.snapshotState()` ДО прогона +
статический `Xoshiro256.fromState()` при материализации → детерминизм
бит-в-бит, тот же seed → те же залежи, что и до R-29 (RNG-серия
`derive('deposits')` не тронута — пул совпадает со старым тоже).

Риски/решения:
- Повторная материализация → дубли залежей? Флаг `depositsMaterialized`
  (в сейве `dm`) выставляется при колонизации; старые сейвы (v1/v2) мигрируются
  при загрузке: любое тело с залежами в гексах = уже материализовано.
- Совместимость: v1/v2 читаются как раньше (expandSaveV2 + миграция флагов);
  сейв владельца (Galaxy #213397) не меняется по содержимому.
- ГГ/луны: у ГГ нет гексов (`ds` не пишем); луны материализуются той же
  функцией, когда появится колонизация лун (хук один, поле одно).

## 2. Формат сейва v3 (`fmt: 3`)

Наследует v2 (кортежи, coord из сетки, округления) и добавляет:

- `galaxy.dict: string[]` — словарь id элементов/руд (первое вхождение при
  обходе); кортежи залежей/пула пишут ИНДЕКС словаря вместо строки:
  `[idx, avail3, qty, depth]`, `[idx, total, avg3, tierIdx, hexCount, max3]`.
- Тело (планета/луна): `ds: [s0,s1,s2,s3]` — RNG-состояние залежей (если есть
  гексы); `dm: 1` — материализовано (пишется только true).
- Кортежи залежей с qty<=0 НЕ пишутся (истощено = отсутствует; добыча и так
  пропускает qty<=0, пул-агрегат не пересчитывается).

Decode: v3 → словарь разворачивается, ds/dm → `depositRngState`/
`depositsMaterialized`; v2 → expandSaveV2 + `migrateLegacyDepositFlags`
(dm=true там, где в гексах есть залежи); v1 → как v2 после парса.

Ожидание по размеру: свежий сейв 200 систем 8.86 МБ → ~3.5 МБ (залежи 6 МБ
исчезают, остаются пулы ~2.5–3 МБ + террейн-гексы ~0.7 МБ + словарь).
