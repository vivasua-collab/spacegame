# Task 28 — Анализ и оптимизация размера сейва (формат v2) + слияние вкладок «Резерв»/«Хранилище»

Дата: 2026-08-31 · Владелец: запрос по итогам R-26/R-27 (сейвы владельцем удалены;
для анализа сгенерирована эталонная галактика seed 42 / 200 систем — конфиг `newGame`)

## Запрос владельца

1. **Расчёт размера сейва** — почему он такой большой? Определить, какие данные
   сохраняются для пустой/условно пустой галактики (дерево: галактика → звёзды →
   планеты → гексы → ресурсы → постройки; склады, наука, корабли дальше).
2. **Схема оптимизации** — возможно, часть полей излишняя
   (в т.ч. вопрос: «ресурсов всего / осталось — нужно ли два поля, одного хватит?»).
3. **UI:** раздельные вкладки «резерв» и «хранилище» объединить; вывод упростить
   до `количество / резерв`; ниже резерва — красный, выше — зелёный.

## Диагноз (scripts/save-size-analysis.ts, форма v1)

Свежая игра (200 систем, 531 планета, 418 лун, 35 369 гексов, 276 427 залежей):
**31.42 МБ plain JSON / 5.26 МБ gzip**. Разложение по сущностям:

| Сущность | МБ | Доля | Причина |
|---|---|---|---|
| Залежи (гексы планет+лун) | 21.88 | 70% | 276 тыс. × объект `{elementId, availability, quantity, depth}`: ~11 МБ — только имена ключей; availability в среднем **18.4 символа** (`0.7168055555555554`) — хвосты float-арифметики, ~8.6 МБ |
| Свод resourceDeposits (планеты+луны) | 6.44 | 20% | ~38 тыс. объектов × 6 полей — те же имена ключей внутри значений |
| Гексы: coord + buildingId:null/Level:0 + deposits:[] | ~2.0 | 6% | coord детерминирован сеткой (индекс массива = индекс сетки); пустые поля застройки у 35 тыс. незастроенных гексов |
| Пустые орбит./атмос. слоты | 0.18 | 0.6% | 2 942 слота, все пустые — не та цель |
| orbitalPeriod, gravity, systemId, луны-orbit* | <0.02 | ~0% | Пересчитываемые/дублируемые поля — экономия нулевая, НЕ трогаем (порог сложности/выгоды) |

Ответы на вопросы владельца:
- **«два поля (всего/осталось) — одного хватит?»** — уже так: в залежи гекса
  хранится ТОЛЬКО `quantity` (остаток); «всего» есть лишь в своде-агрегате.
  Дублей нет.
- **«постройки вынести в отдельную часть — не дублирование?»** — постройки
  лежат ВНУТРИ гексов/слотов (`buildingId`/`buildingLevel`) — второй сущности
  нет, дублирования нет. С отдельной секцией она бы появилась.
- **Агрегат resourceDeposits нельзя дропнуть/пересчитать из гексов**:
  `aggregateResourceDeposits()` добавляет RNG-контент (гарантированные
  элементы таблицы, hexCount=0, и 1-2 ультраредких) — его в гексах НЕТ.
  Отказ от «дельта против seed»: любая правка генерации (см. R-26 — полосы
  гравитации) инвалидировала бы все сейвы.

## Решение: формат v2 (маркер `fmt: 2` в корне JSON)

Кодек `src/lib/save-format-v2.ts` (encode в `serializeGameState`, decode в
`deserializeGameState` ДО zod-валидации):

1. **Залежи → кортежи** `[elementId, availability, quantity, depth]`,
   availability — 3 знака (семантика генератора уже 0.001).
2. **Свод → кортежи** `[elementId, totalQuantity, avgAvailability, tierIdx, hexCount, maxAvailability]`, tierIdx 0/1/2 — RNG-контент сохраняется полностью.
3. **Гексы:** без `coord` (восстановление `generateHexCoords(length)[i]` —
   экспорт из hex-grid.ts; порядок массива = порядок сетки, count неизменен);
   без `buildingId/buildingLevel` у незастроенных (→ null/0); без `deposits: []`.
4. **Звёзды:** mass/luminosity/temperature/radius → 4 значащих цифры.
5. **Слоты НЕ сжимаются** (0.6% выгоды, ГГ-слоты RNG-зависимы — нужно поле-счётчик).
6. Обратная совместимость: сейвы без `fmt:2` читаются как раньше (v1);
   идемпотентность encode(decode(encode(s))) === encode(s) (округления стабильны).
7. Чистая функция: живой state не мутируется (строятся новые объекты).

Результат (200 систем): **31.42 → 8.86 МБ plain (−71.8%)**, gzip 5.26 → 2.28 МБ;
БД хранит v2 (место под сейвы ×3.5). Инструмент: `bun run save:size`.

## UI: единый список «Хранилище · количество / резерв»

`planet-view.tsx` (WarehousePanel): секции «Резервы» и «Хранимые ресурсы»
