# План: Task ID 26 — Гравитационная градация планет + транспорт сохранений (gzip) + инспекция дампа
Дата: 2026-08-31 · Источник: владелец — «планета 0.9g — средняя, а 0.8g — большая; ледяная 0.4g —
большая. Необходима чёткая градация: чем планета больше (в рамках одного геологического типа),
тем гравитация выше. Реализовать чтение дампа (сейва) галактики для анализа агента. Ошибка
сохранения: EntityTooLarge 33554432 bytes (шлюз), подозрение на устаревшую структуру модуля сохранения».

## Диагноз (зафиксирован)

1. **Гравитация не упорядочена**: `generatePlanet` тянет радиус и плотность как НЕЗАВИСИМЫЕ
   случайные величины → `g = R×ρ/5.51` может инвертироваться между классами (ледяная R=1.9/ρ=1.6
   → 0.44g «большая», скалистая R=1.0/ρ=8.0 → 1.45g «средняя»). Класс размера = `getSizeFromRadius`
   (глобальные пороги R⊕), полосы гравитации классов пересекаются.
2. **EntityTooLarge**: замер — 200 систем → state 30.7MB (почти лимит шлюза 32MB, при росте
   состояния в игре превышает), 500 систем → 79.3MB. gzip: 5.2/13.3MB, base64: 6.9/17.7MB —
   под лимитом. Сериализация `serializeGameState` НЕ устарела (spread `...state` включает все
   новые поля; systemMap/bakedModel вырезаются и регенерируются) — проблема только в размере
   транспорта.
3. **Дамп для анализа**: нет инструмента чтения сейва из БД.

## Цели

1. Типоспецифичные **гравитационные полосы по классам размера** (PLANET_GRAVITY_BANDS /
   MOON_GRAVITY_BANDS): внутри класса g линейно растёт с радиусом, полосы соседних классов
   НЕ пересекаются → «больше планета → выше g» строго. Плотность выводится из g и R
   (физическая согласованность), остаётся в пределах диапазона типа. RNG-последовательность
   генерации сохранена (снапшоты не сдвигаются).
2. **Транспорт сохранений**: клиент gzip+base64 (CompressionStream) → POST/PUT `stateEncoding:
   'gzip-base64'` → сервер gunzip (node:zlib) → валидация ≤50MB raw → хранение plain JSON
   (version 1, совместимо). GET [id]: state > 512KB отдаётся gzip-base64. Fallback на plain
   при отсутствии CompressionStream.
3. **Инструмент анализа**: `scripts/inspect-save.ts` (`bun run save:inspect [--id=…]`) —
   дамп последнего сейва в `scripts/output/save-dump.json` + сводка: матрица тип×размер,
   min/max/avg гравитации, проверка инверсий и согласованности формулы, метрики состояния.
4. Тесты: градация (полосы, разделение классов, монотонность R→g, регрессия «лёд 0.4g ≠ большая»,
   луны, согласованность плотности), API-кодирование (POST/PUT/GET gzip-base64, лимит raw,
   битый payload), round-trip клиентского кодека.
5. Доки: 30-planets.md §2.2 (полосы + таблица), STATUS changelog. Гейты: lint 0 / tsc ≤156 /
   тесты / validate:all. Браузерная верификация: новая игра → планеты → сохранение успешно →
   инспекция реального сейва.

## Открытые вопросы

- Хранить в БД сжатое или plain? → Решение: plain JSON (version 1) — совместимость, простота
  инспекции; сжимается только транспорт (шлюз 32MB).
- Менять ли RNG-вызовы генерации? → Решение: НЕТ — сохраняем точную последовательность
  (плотность продолжает вытягиваться, но используется только в fallback) → снапшоты стабильны.
- 500 систем raw 79MB > 50MB zod-лимита? → Решение: лимит сохраняется (существующая политика
  Block 08); документируется. Игровой UI = 200 систем (30.7MB → gzip 5.2MB) — проходит.
